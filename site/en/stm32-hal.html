01

认识 STM32 与 HAL 开发方式第一篇 · HAL 与工具

P1 – P5　·　6 节　·　4 题

入门

STM32 的开发方式有三层：直接写寄存器、调标准库、用 HAL 库。HAL 不是「更高级的语言」，而是 ST 把「配哪个寄存器、按什么顺序配」封装成函数，让你把时间花在业务上。这一课先把三种写法摆在一起，弄清 HAL 的边界，再认识 F103C8T6 这颗芯片和它的最小系统。

读完这一课你能做到

  • 能说出寄存器、标准库、HAL/LL 三种开发方式各自的优缺点和适用场景
  • 能画出 CMSIS → HAL → 用户代码这三层的关系，知道 CubeMX 生成的是哪一层
  • 能读懂 STM32F103C8T6 的型号、资源、引脚命名与最小系统四要素
  • 知道 HAL 工程的固定节奏：CubeMX 配 → 生成代码 → 只在 USER CODE 区写业务
一、同一颗芯片，三种写法

点一颗 LED，本质都是「把 GPIOA 的第 8 位置 0」。三种写法的差别不在硬件，而在「谁来记住寄存器地址和配置顺序」。

写法点灯代码（核心一行）优点代价
直接操作寄存器GPIOA->BRR = GPIO_PIN_8;最快、代码最小、完全可控每个外设都要翻参考手册；换型号要重写
标准外设库 SPLGPIO_ResetBits(GPIOA, GPIO_PIN_8);函数名直观、资料多ST 已停止维护，只覆盖 F1/F2/F4/L1 等老系列
HAL 库HAL_GPIO_WritePin(GPIOA, GPIO_PIN_8, GPIO_PIN_RESET);全系列统一接口、CubeMX 自动生成、生态完整多一层封装，代码略大、执行略慢

这三种写法没有「谁更专业」。HAL 适合快速做出产品、适合跨系列移植；寄存器适合抠时序、抠体积；标准库适合维护老工程。本站两门单片机课就是前两种写法的对照：标准库 19 课 与这一门 HAL 24 课。

LL 库：HAL 的「轻量版」

ST 从 CubeF1 起同时发布 LL（Low Layer）库，它和 HAL 捆绑在同一个固件包里，头文件以 _ll_ 命名。LL 直接操作寄存器，效率接近手写寄存器；HAL 的很多函数内部也会调用 LL。两者的分工：

  • 要跨系列、要图形化配置、要中间件（USB/FATFS/FreeRTOS） → 用 HAL；
  • 要极致的时序或代码体积、又不想完全手写寄存器 → 用 LL；
  • 同一个工程里可以混用：CubeMX 里把某个外设的 Use Full LL 打开即可。
二、HAL 库到底是什么

HAL = Hardware Abstraction Layer（硬件抽象层）。它不改变硬件，只是在「寄存器」和「你的代码」之间加了一层函数。这层函数遵守 ARM 的 CMSIS 规范，所以同一套 API 能覆盖 STM32 全系列。

层里面有什么谁维护你要不要看
CMSIS-Corecore_cm3.h、NVIC/SysTick 的内核访问、启动文件ARM知道有这层即可
CMSIS-Devicestm32f103xb.h、外设寄存器结构体、中断号ST查寄存器时看
HAL 驱动stm32f1xx_hal_gpio.c、stm32f1xx_hal_uart.c…ST出问题时要看
用户代码main.c、gpio.c、usart.c 里的业务你天天写

HAL 的命名有固定规律，记住这套规律，看函数名就知道它干什么：

形式例子含义
HAL_<外设>_Init()HAL_GPIO_Init()用句柄里的参数初始化外设
HAL_<外设>_<动作>()HAL_UART_Transmit()读、写、启动、停止等动作
HAL_<外设>_<动作>_IT()HAL_ADC_Start_IT()中断方式版本
HAL_<外设>_<动作>_DMA()HAL_UART_Receive_DMA()DMA 方式版本
HAL_<外设>_xxxCallback()HAL_UART_RxCpltCallback()弱函数，中断处理完成后回调给你
HAL_<外设>_MspInit()HAL_UART_MspInit()弱函数，放时钟、引脚、NVIC 等底层初始化
__HAL_<外设>_<动作>__HAL_RCC_GPIOA_CLK_ENABLE()宏，直接操作某一位或使能时钟

句柄与初始化结构体

HAL 每个外设都有一个句柄（UART_HandleTypeDef huart1），句柄里又嵌一个初始化结构体（huart1.Init）。CubeMX 生成的 MX_USART1_UART_Init() 就是「填结构体 → 调 HAL_UART_Init()」。理解这一点，后面所有外设都是同一个套路：

UART_HandleTypeDef huart1;          /* 句柄：外设实例 + 运行状态 + 参数 */

huart1.Instance          = USART1;  /* 用哪个硬件 */
huart1.Init.BaudRate     = 115200;  /* 工作参数 */
huart1.Init.WordLength   = UART_WORDLENGTH_8B;
huart1.Init.StopBits     = UART_STOPBITS_1;
huart1.Init.Parity       = UART_PARITY_NONE;
huart1.Init.Mode         = UART_MODE_TX_RX;
huart1.Init.HwFlowCtl    = UART_HWCONTROL_NONE;
huart1.Init.OverSampling = UART_OVERSAMPLING_16;

if (HAL_UART_Init(&huart1) != HAL_OK) {
    Error_Handler();                /* 初始化失败：时钟/引脚/参数有一处不对 */
}
三、F103C8T6 的家底与最小系统

STM32F103C8T6 每一位都在说参数：C = 48 脚，8 = 64KB Flash，T = LQFP，6 = -40～85℃。它属于 F1 的「中容量」产品，CubeMX 里对应 STM32F103C8Tx。

资源实际值对 HAL 开发的影响
内核 / 主频Cortex-M3，72MHzHAL 的 HAL_Delay(1) 精度 1ms，来自 SysTick
Flash / SRAM64KB / 20KBCubeMX 勾「Copy only necessary」后，F1 HAL 工程约 10–20KB
通用 IO37 个（PA0–15、PB0–15、PC13–15）CubeMX 左侧点引脚即可分配
定时器TIM1 高级；TIM2/3/4 通用；TIM6/7 基本PWM、捕获、编码器都能练
通信3×USART、2×I2C、2×SPI、1×CAN、1×USB第 10–11、18–19、23 课覆盖
模拟2×ADC（12 位），无 DACDAC 课用 F103RC 以上或 PWM+RC 替代
调试SWD（PA13/PA14）不要把这俩配成普通 IO

最小系统只保证芯片能跑，四样缺一不可：

  1. 电源：3.3V LDO + 每个电源脚 100nF 去耦；
  2. 晶振：8MHz + 两个 20pF 负载电容（HAL 的 SystemClock_Config 默认按 8MHz 算）；
  3. 复位：NRST 10kΩ 上拉 + 100nF 到地 + 按键；
  4. 启动配置：BOOT0 经 10kΩ 下拉到地。

再加 SWD 排针（3.3V / GND / SWDIO / SWCLK）就能下载调试。买板子重点看 BOOT0 是否有下拉、晶振是不是 8MHz——这两处不对，后面 CubeMX 的时钟树怎么配都不对。

四、HAL 开发的固定节奏

HAL 工程不是「从空 main.c 开始写」，而是「CubeMX 生成骨架，你只填业务」。固定节奏只有四步：

第 1 步：在 CubeMX 里配硬件

选芯片 → 配 RCC 时钟源（HSE 晶振）→ 配 SYS 调试口（Serial Wire）→ 点引脚设功能 → 在 Clock Configuration 里拉时钟树 → 配外设参数与 NVIC → Project Manager 选 MDK-ARM、填工程名、生成代码。

第 2 步：CubeMX 生成初始化代码

生成后每个外设一个 xxx.c（GPIO 在 gpio.c，串口在 usart.c），里面是 MX_xxx_Init()；main.c 里按 HAL_Init() → SystemClock_Config() → MX_GPIO_Init() → … 的顺序调用。这些生成代码不要手改，下次重新生成会被覆盖。

第 3 步：只在 USER CODE 区写业务

CubeMX 在每个函数里留了注释对：

/* USER CODE BEGIN 2 */
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_8, GPIO_PIN_RESET);   /* 你的代码放这里 */
/* USER CODE END 2 */

只有 USER CODE BEGIN/END 之间的内容会被 CubeMX 保留。写在区间外的代码，重新生成一次就没了——这是 HAL 新手最常见的事故。

第 4 步：编译、下载、看现象

Keil 里 F7 编译、F8 下载；Debug 里可以打开 Peripherals → System Viewer 直接看 GPIO/USART/TIM 寄存器，比只读代码快得多。

  1. HAL 库、标准库、直接写寄存器，三者的本质区别是什么？HAL 为什么能做到「全系列同一套接口」？

    本质区别是「谁负责把硬件动作翻译成寄存器操作」：寄存器写法由程序员直接面对地址与位；标准库用一层函数包装寄存器；HAL 在标准库之上再抽象出统一的句柄、初始化结构体与回调，把不同系列的外设差异藏在驱动内部。全系列兼容靠两层：ARM 的 CMSIS 统一内核访问，ST 的 HAL 驱动为每个系列实现同一组 API，用户代码只依赖 API 名字，不依赖寄存器地址。

  2. 句柄（HandleTypeDef）和初始化结构体（InitTypeDef）是什么关系？为什么要分成两个？

    句柄描述「一个外设实例的完整状态」：用哪个硬件（Instance）、当前工作参数（Init）、运行时的缓冲区指针、状态机、错误码等。InitTypeDef 只是其中「初始化参数」这一小块。分成两个是为了让运行期状态和静态配置解耦：初始化时用 Init 填参数，运行中 HAL 会改写句柄里的 State/ErrorCode，但不会动 Init；用户也可以在不重新 Init 的情况下修改某个参数再调用相应函数。

  3. 在 CubeMX 生成的工程里，为什么不能直接改 MX_GPIO_Init() 里的代码？如果确实需要改配置，正确做法是什么？

    因为 MX_GPIO_Init() 属于生成区，CubeMX 重新生成时会按 .ioc 文件重写整个函数，手改会丢失。正确做法是回到 CubeMX 修改引脚/参数并重新生成；如果只是运行时要改变行为（比如翻转电平、切换上下拉），在 USER CODE 区调用 HAL 函数，而不是改初始化代码。确实要永久改初始化，可以在 USER CODE BEGIN 里追加自己的配置，或在生成区外另写一个 My_GPIO_Init() 覆盖。

  4. 一块 C8T6 最小系统板，接上 3.3V 和 ST-Link 后程序能下载但完全不跑。按顺序先查哪三处？

    ① BOOT0：必须为低（接 GND），否则可能从系统存储器启动，不跑用户 Flash；② 复位与供电：量 NRST 是否为高、3.3V 是否稳定，复位电容是否短路；③ 时钟：确认晶振是 8MHz、SystemClock_Config() 没有把 PLL 配到超频；如果程序卡在 Error_Handler()，就是 HSE 起振失败。三步都正常，再用 Debug 单步看是否进了 main()。

int main(void)

  MX_GPIO_Init();                   /* 3. CubeMX 生成的外设初始化 */
  /* USER CODE BEGIN 2 */
  /* 你的初始化放这里 */
  /* USER CODE END 2 */

  {

    HAL_Delay(500);
    /* USER CODE END 3 */
  }
}

  1. CubeMX 生成工程时，Copy only the necessary library files 勾与不勾有什么区别？各自适合什么场景？

    勾上时 CubeMX 只把本工程用到的 HAL 驱动 .c 文件复制进 Drivers，工程体积小、编译快；不勾则链接到固件包安装目录（或复制完整库），体积大但换外设不用重新生成。学习阶段建议勾上，工程自包含、换电脑也能编译；如果要做多个外设频繁迭代，也可以不勾，减少重复复制。

  2. main.c 里 HAL_Init()、SystemClock_Config()、MX_GPIO_Init() 三者的顺序能不能换？为什么？

    不能随便换。HAL_Init() 必须先做：它设置 Flash 预取/等待周期、初始化 SysTick 的时基，并调用 HAL_MspInit()；没有它，后面的 HAL_Delay 和中断都没法正常工作。SystemClock_Config() 必须在所有外设初始化之前：外设的波特率、定时器分频都按最终主频计算，先配外设再改主频会全错。MX_GPIO_Init() 依赖时钟，放在时钟配置之后。

  3. 为什么 CubeMX 生成的 MX_USART1_UART_Init() 里看不到 GPIO 和时钟配置？它们在哪里？

    CubeMX 把「外设参数」放在 MX_USART1_UART_Init()，把「底层资源」——GPIO 复用、外设时钟、NVIC——放在 HAL_UART_MspInit()（在 usart.c 或 stm32f1xx_hal_msp.c 里）。HAL_UART_Init() 内部会调用 HAL_UART_MspInit()。这样分层的好处是：换引脚/换时钟只改 MSP，不动外设参数；用户也可以重写 MSP 接管底层初始化。

  4. 手上只有一块新板，没有 ST-Link，只有 USB 转 TTL。能不能把程序下载进去？步骤是什么？

    能，用串口 ISP（系统存储器启动）。步骤：① BOOT0 接 3.3V、BOOT1 接 GND；② 复位，芯片从 System Memory 启动，内置 bootloader 监听 USART1（PA9/PA10）；③ USB-TTL 交叉接 PA9/PA10 并共地；④ 用 FlyMcu / STM32CubeProgrammer 选串口、加载 .hex、开始编程；⑤ 下载完把 BOOT0 接回 GND，再复位从 Flash 启动。注意串口 ISP 不能调试，且部分板子的 BOOT1 是复用脚，接线前查原理图。

二、HAL 的「三件套」：Init、MSP、Callback

这是理解 HAL 的关键。任何一个外设的初始化都分三层：

第 1 层：HAL_xxx_Init() —— 配外设本身

用句柄里的参数写外设寄存器，例如 HAL_UART_Init(&huart1) 写波特率、字长、停止位、校验位。它只关心外设，不碰 GPIO 和时钟。

第 2 层：HAL_xxx_MspInit() —— 配底层资源

MSP = MCU Support Package。HAL_xxx_Init() 内部会调用它（弱函数，默认空），你要在这里放：

  • 外设时钟使能：__HAL_RCC_USART1_CLK_ENABLE()；
  • GPIO 复用与模式：HAL_GPIO_Init()；
  • 中断优先级与使能：HAL_NVIC_SetPriority/EnableIRQ；
  • DMA 通道配置。

CubeMX 自动生成的 usart.c 里就有 HAL_UART_MspInit()，把这几件事都写好了。

第 3 层：HAL_xxx_Callback() —— 中断/传输完成后的业务

stm32f1xx_hal_uart.c 里的中断服务函数只做「清标志、判类型」，然后调用弱函数回调：

__weak void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
  /* 空函数，等用户重写 */
}

你在 main.c 或自己的 .c 里重新定义同名函数，HAL 就会调用你的版本。这就是 HAL 不用改驱动就能加业务的原因。

/* 用户重写：串口收到一个字节后自动进来 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART1) {
        HAL_UART_Transmit(&huart1, &rx_byte, 1, 10);   /* 原样回显 */
        HAL_UART_Receive_IT(&huart1, &rx_byte, 1);     /* 重新挂接收 */
    }
}

四、生成代码的调用链

以串口为例，把整条链串起来看：

main()
 ├─ HAL_Init()
 │   └─ HAL_MspInit()                  ← 系统级底层（时钟、SWD 等）
 ├─ SystemClock_Config()              ← 72MHz
 ├─ MX_GPIO_Init()                    ← GPIO 时钟 + 引脚
 ├─ MX_USART1_UART_Init()
 │   ├─ huart1.Init = ...             ← 填参数
 │   └─ HAL_UART_Init(&huart1)
 │       └─ HAL_UART_MspInit()        ← 串口时钟 + PA9/PA10 复用 + NVIC
 └─ while(1)
     └─ HAL_UART_Receive_IT()         ← 开中断接收
         └─ (收到数据) USART1_IRQHandler()
             └─ HAL_UART_IRQHandler()
                 └─ HAL_UART_RxCpltCallback()   ← 你的业务

看懂这条链，后面所有外设都能套：Init 配外设、MSP 配底层、IRQHandler 清标志、Callback 写业务。

  1. HAL_UART_Init() 与 HAL_UART_MspInit() 的分工是什么？为什么 HAL 要把它们拆开？

    HAL_UART_Init() 只写 USART 外设自己的寄存器（波特率、字长、停止位、校验、模式），属于「外设参数」；HAL_UART_MspInit() 负责让外设「能用」的底层条件：RCC 时钟、GPIO 复用、NVIC、DMA。拆开是为了可移植：换板子只改 MSP（引脚/时钟），外设参数和业务代码不动；同时 MSP 是弱函数，用户可以在不修改 HAL 驱动的前提下接管底层。

  2. 什么是 __weak 函数？如果用户不重写 HAL_UART_RxCpltCallback()，中断来了会发生什么？

    __weak 是编译器属性，表示「这个函数可以被同名强定义覆盖」。HAL 在驱动里给每个回调一个空的弱定义；链接时如果用户提供了同名函数，就用用户的版本，否则用空的。用户不重写时，接收完成中断仍会被 HAL 清除标志并返回，只是没有任何业务动作，数据不会自动处理——看起来像「中断进了但没反应」。

  3. CubeMX 的 Generate peripheral initialization as pair of .c/.h 勾与不勾，生成结构有什么不同？

    勾上时每个外设生成独立的 gpio.c/h、usart.c/h，main.c 只调用 MX_xxx_Init()，结构清晰，适合多外设工程；不勾则所有初始化都塞进 main.c，文件少但很长，改起来容易冲突。建议勾上，和本站代码结构一致。

  4. 为什么 CubeMX 生成工程时要求路径不能有中文/空格？已经生成了中文路径的工程，怎么补救？

    Keil 的编译器和 Makefile 对非 ASCII 路径、空格处理不好，容易出现找不到源文件、链接路径截断。补救：把整个工程目录移到纯英文路径（如 D:\mcu\Blink），用 CubeMX 重新打开 .ioc 并重新生成，再在 Keil 里改 Output/Listing 路径；不要只改文件夹名，工程文件里的相对路径也要跟着更新。

基础

时钟是单片机的「节拍器」：内核、总线、定时器、串口全按它计时。HAL 把所有时钟配置收进 SystemClock_Config()，但 CubeMX 只是替你填数，算错的后果仍然是波特率乱码、定时器差两倍、ADC 采样超速。这一课把 F1 的时钟树拆开，再把 SysTick 这个 1ms 心跳讲透。

  • 能解释为什么 APB1 是 36MHz，而挂在 APB1 上的 TIM2/3/4 仍然是 72MHz
  • 能读懂并手写 SystemClock_Config()，知道每个结构体成员对应哪个寄存器
  • 能说清 SysTick 如何产生 1ms 中断、uwTick 与 HAL_Delay 的关系
一、四个时钟源：先从哪儿起振

F1 有四个时钟源，CubeMX 的 RCC 页面就是让它们起振：

时钟源频率来源典型用途
HSI8MHz内部 RC上电默认、HSE 失效时的后备
HSE4–16MHz（板载 8MHz）外部晶振PLL 输入，主频的基准
LSI~40kHz内部 RC独立看门狗 IWDG、RTC 后备
LSE32.768kHz外部晶振RTC 精确走时

上电复位后，芯片先跑 HSI 8MHz；SystemInit()（启动文件调用）会把时钟切到 HSE+PLL（如果 stm32f1xx_hal_conf.h 里 HSE_VALUE 与板子一致）。真正的「72MHz」是 SystemClock_Config() 跑完才稳定的。

二、时钟树：72MHz 是乘出来再分下去的
HSE 8MHz ──► PLL Source ──► PLL ×9 ──► SYSCLK 72MHz
                                      ├─ AHB ÷1 ──► HCLK 72MHz（内核、DMA、SRAM、Flash）
                                      ├─ APB2 ÷1 ─► PCLK2 72MHz（GPIO、AFIO、USART1、ADC1/2、TIM1、SPI1）
                                      └─ APB1 ÷2 ─► PCLK1 36MHz（USART2/3、I2C1/2、SPI2、TIM2/3/4、PWR、BKP、WWDG）

三条硬约束：

  • SYSCLK ≤ 72MHz；
  • APB1 ≤ 36MHz，所以 APB1 预分频至少 ÷2；
  • ADC 时钟 ≤ 14MHz，ADC 预分频通常 ÷6（72/6 = 12MHz）。

最容易记错的一条：APB 预分频 ≠ 1 时，定时器时钟 = PCLK × 2。所以 TIM2/3/4 挂在 36MHz 的 APB1 上，但计数时钟是 72MHz；I2C1 没有这个翻倍，仍然是 36MHz。PWM 频率算不对，十有八九是把这两者搞混了。

三、CubeMX 里怎么配
  1. RCC → HSE 选 Crystal/Ceramic Resonator；
  2. Clock Configuration 页，在 HCLK 框输入 72 回车；
  3. CubeMX 自动把 PLL Source 选为 HSE、PLLMul 设为 ×9、APB1 Prescaler 设为 ÷2、ADC Prescaler 设为 ÷6；
  4. 看右上角的 Clock Tree 是否全绿；红框表示超限；
  5. 生成代码后，main.c 里会多出 SystemClock_Config()。

如果板子是 12MHz 晶振，HSE 输入要改成 12，PLL 倍频改 ×6，否则会算出 108MHz 超频跑飞。换板先量晶振，这是最省时间的习惯。

四、SystemClock_Config() 逐行读

HAL 1.8 的 F1 代码长这样（CubeMX 生成，略有删减）：

void SystemClock_Config(void)
{
  RCC_OscInitTypeDef RCC_OscInitStruct = {0};
  RCC_ClkInitTypeDef RCC_ClkInitStruct = {0};

  /* 1. 选振荡器：HSE 开、PLL 源选 HSE、倍频 ×9 */
  RCC_OscInitStruct.OscillatorType = RCC_OSCILLATORTYPE_HSE;
  RCC_OscInitStruct.HSEState       = RCC_HSE_ON;
  RCC_OscInitStruct.HSEPredivValue = RCC_HSE_PREDIV_DIV1;
  RCC_OscInitStruct.HSIState       = RCC_HSI_ON;
  RCC_OscInitStruct.PLL.PLLState   = RCC_PLL_ON;
  RCC_OscInitStruct.PLL.PLLSource  = RCC_PLLSOURCE_HSE;
  RCC_OscInitStruct.PLL.PLLMUL     = RCC_PLL_MUL9;
  if (HAL_RCC_OscConfig(&RCC_OscInitStruct) != HAL_OK) {
    Error_Handler();
  }

  /* 2. 选系统时钟源与各总线分频 */
  RCC_ClkInitStruct.ClockType      = RCC_CLOCKTYPE_HCLK | RCC_CLOCKTYPE_SYSCLK
                                   | RCC_CLOCKTYPE_PCLK1 | RCC_CLOCKTYPE_PCLK2;
  RCC_ClkInitStruct.SYSCLKSource   = RCC_SYSCLKSOURCE_PLLCLK;
  RCC_ClkInitStruct.AHBCLKDivider  = RCC_SYSCLK_DIV1;
  RCC_ClkInitStruct.APB1CLKDivider = RCC_HCLK_DIV2;
  RCC_ClkInitStruct.APB2CLKDivider = RCC_HCLK_DIV1;

  /* 3. 72MHz 需要 2 个 Flash 等待周期 */
  if (HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_2) != HAL_OK) {
    Error_Handler();
  }
}

三个细节：

  • FLASH_LATENCY_2：72MHz 时 Flash 取指要等 2 个周期，配错会取指错误/死机；
  • HSEPredivValue：F1 的 PLL 输入前有一个 ÷1/÷2 预分频，8MHz 用 ÷1；
  • HAL_RCC_ClockConfig() 内部会更新 SystemCoreClock，但**如果你手动改了时钟而没调这个函数，SystemCoreClock 还是旧值**，HAL_Delay 和串口都会算错。
五、SysTick：HAL 的 1ms 心跳

SysTick 是 Cortex-M3 内核自带的 24 位递减计数器，不属于任何外设，所以不受 APB 分频影响，始终按 HCLK 计数。

/* HAL_Init() 内部会调用 HAL_InitTick(TICK_INT_PRIORITY) */
__weak HAL_StatusTypeDef HAL_InitTick(uint32_t TickPriority)
{
  /* 重装值 = 72MHz / 1000 - 1 = 71999，每 1ms 中断一次 */
  HAL_SYSTICK_Config(SystemCoreClock / (1000U / uwTickFreq));
  HAL_SYSTICK_CLKSourceConfig(SYSTICK_CLKSOURCE_HCLK);
  HAL_NVIC_SetPriority(SysTick_IRQn, TickPriority, 0U);
  return HAL_OK;
}

/* SysTick_Handler → HAL_IncTick()：每 1ms 把全局计数 +1 */
void SysTick_Handler(void)
{
  HAL_IncTick();
  HAL_SYSTICK_IRQHandler();   /* 只有用了 HAL 的 SysTick 回调才需要 */
}

由此得到两个最常用的函数：

函数实现用途
HAL_GetTick()返回全局 uwTick非阻塞超时、状态机计时
HAL_Delay(ms)记录起点，循环等 uwTick - start >= ms简单阻塞延时

uwTick 是 uint32_t，49.7 天溢出一次；写超时判断时用「差值」而不是「大小」：if (HAL_GetTick() - start > 100)，溢出也正确。

时基可以换

用 FreeRTOS 时，SysTick 被 RTOS 占用，CubeMX 会把 SYS → Timebase Source 改成 TIMx，并生成 HAL_TIM_Base_Start_IT()。这时 HAL_Delay 仍然可用（时基换成 TIM 中断），但精度与中断优先级要重新评估。

  1. 8MHz HSE、PLL×9、AHB÷1、APB2÷1、APB1÷2 的配置下，SYSCLK、HCLK、PCLK2、PCLK1、TIM2 计数时钟、I2C1 时钟各是多少？

    SYSCLK = 8×9 = 72MHz；HCLK = 72/1 = 72MHz；PCLK2 = 72/1 = 72MHz；PCLK1 = 72/2 = 36MHz；TIM2 挂在 APB1，APB1 预分频≠1，所以定时器时钟 = 36×2 = 72MHz；I2C1 不享受翻倍，仍是 36MHz。

  2. 为什么 72MHz 时 HAL_RCC_ClockConfig() 要传 FLASH_LATENCY_2？传 0 会怎样？

    Flash 的读取速度跟不上 72MHz 的内核，需要插入等待周期：F1 在 48–72MHz 范围要求 2 个等待周期。传 0 表示零等待，CPU 取指时 Flash 还没准备好，会读到错误指令/总线错误，表现为随机死机或 HardFault。等待周期数与主频、供电电压有关，CubeMX 会按频率自动选，手写时不要省。

  3. HAL_Delay(1000) 的内部实现是什么？在中断服务函数里调用它有什么风险？

    它先记录 HAL_GetTick()，然后 while (HAL_GetTick() - start < 1000) 空转。uwTick 由 SysTick 中断每 1ms 加 1，所以延时依赖 SysTick 中断能被响应。如果在优先级不低于 SysTick 的中断里调用，SysTick 被屏蔽，uwTick 不再增长，程序会永远卡在 while 里（看门狗随后复位）。中断里要用非阻塞状态机或硬件定时器，不要用 HAL_Delay。

  4. 用 FreeRTOS 时，为什么 CubeMX 建议把 Timebase Source 从 SysTick 改成 TIM？不改会怎样？

    FreeRTOS 要把 SysTick 用作自己的系统节拍，并在 SysTick_Handler 里做任务调度；HAL 的 HAL_IncTick() 如果和 RTOS 抢同一个中断，轻则延时不准，重则调度器节拍被覆盖。改成 TIM 后，HAL 用独立的定时器中断维护 uwTick，SysTick 完全归 RTOS，两者互不干扰。代价是多占一个定时器，并且这个 TIM 的中断优先级要设得比 RTOS 可管理范围高（通常最高）。

一、延时：毫秒用 SysTick，微秒用 DWT

毫秒级：HAL_Delay

void HAL_Delay(uint32_t Delay)
{
  uint32_t tickstart = HAL_GetTick();
  while ((HAL_GetTick() - tickstart) < Delay) { }
}

优点：简单、跨系列统一。缺点：阻塞，延时期间 CPU 空转；在中断里调用可能死等（SysTick 被屏蔽）；最小分辨率 1ms，且实际会比设定多 0–1ms（取决于进入时刻）。

微秒级：DWT 周期计数器

F1 的 Cortex-M3 有 DWT（Data Watchpoint and Trace）周期计数器，按 HCLK 计数，精度到 1/72MHz ≈ 13.9ns：

/* 初始化：使能 DWT 周期计数器 */
void DWT_Delay_Init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;  /* 打开 trace */
    DWT->CYCCNT = 0;
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;            /* 使能计数 */
}

/* 忙等 us 微秒；72MHz 下 1us = 72 个周期 */
void DWT_Delay_us(uint32_t us)
{
    uint32_t start = DWT->CYCCNT;
    uint32_t ticks = us * (SystemCoreClock / 1000000U);
    while ((DWT->CYCCNT - start) < ticks) { }
}

DWT 不受中断影响，适合给 WS2812、单总线、软件 I2C 这类「微秒级时序」用；它仍然是忙等，长延时不要用它。

非阻塞延时：状态机

要同时做多件事，就不要「等」：

static uint32_t last;
if (HAL_GetTick() - last >= 500) {
    last = HAL_GetTick();
    HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_8);   /* 每 500ms 干一次，不阻塞 */
}

四、从上电到 main()：中间发生了什么
上电/复位
  ├─ 内核从 0x08000000 取 MSP 初值（栈顶）
  ├─ 从 0x08000004 取 Reset_Handler 地址并跳转
  ├─ Reset_Handler（startup_stm32f103xb.s）
  │   ├─ SystemInit()          ← 配 Flash 等待周期、向量表、时钟（HAL 工程里通常不配 PLL）
  │   ├─ __main()              ← 编译器运行库：拷 .data、清 .bss、初始化栈堆
  │   └─ main()
  │       ├─ HAL_Init()        ← 复位外设、Flash 接口、SysTick
  │       ├─ SystemClock_Config()
  │       └─ MX_xxx_Init() ...

几个容易忽略的事实：

  • 中断向量表必须在 Flash 起始处（或重映射到 SRAM），所以 SCB->VTOR 一般不改；
  • SystemInit() 不等于 SystemClock_Config()：前者是启动文件里调的最简初始化，后者是 HAL/CubeMX 生成的完整时钟配置；
  • 全局变量初值在 .data（有初值）和 .bss（零初始化）里，__main 负责搬运/清零；未初始化的局部变量是随机值。

段含义放在哪

  1. HAL_Delay(1) 的实际延时为什么可能超过 1ms？在 1ms 精度不够的场合应该换什么？

    HAL_Delay 以 SysTick 的 1ms 中断为基准：如果调用时刚好错过一个 tick，就要多等接近 1ms；中断被更高优先级打断时也会拉长。要求更高时：微秒级用 DWT 周期计数器；需要严格周期用硬件定时器中断/PWM；需要不阻塞用 HAL_GetTick() 差值做状态机。

  2. Keil 下 printf 重定向为什么必须勾 MicroLIB？不勾会发生什么？

    Keil 的 ARM 编译器默认使用标准 C 库，标准库的底层 I/O 走半主机（semihosting），需要调试器接管 BKPT 指令；没有调试器时程序会停在异常。MicroLIB 是精简库，不做半主机初始化，重定向 fputc 后直接走串口。也可以不勾 MicroLIB 但显式关闭 semihosting（加 __use_no_semihosting 并实现 _sys_exit 等），更麻烦。

  3. BOOT0=1、BOOT1=0 时芯片从哪里启动？这个模式有什么实际用途？下载完要注意什么？

    从系统存储器（System Memory）启动，里面是 ST 出厂固化的 bootloader，支持 USART1/USB 等接口的 ISP 下载。用途：没有 SWD 调试器时给芯片烧程序、救砖。下载完成后必须把 BOOT0 接回 GND 并复位，否则每次上电都进 bootloader，用户程序不会运行。

  4. MAP 文件里 ZI Data 很大，但程序还能跑；换一个大数组后随机死机，最可能的原因是什么？怎么定位？

    ZI Data 包含栈和堆的预留空间，MAP 里给出的是链接时分配的总量，不代表运行时都用满。大数组会挤占 RAM，最容易先撑爆栈（栈从 RAM 顶端向下增长，越界会改写全局变量）。定位：看 MAP 的 Stack_Size 与 Heap_Size，把大数组改成 static/全局并检查剩余 RAM；在调试器里看 MSP 当前值与栈底距离；或把栈加大后复现是否消失。

基础

GPIO 看着最简单，其实是「数字电路 + 模拟开关 + 复用矩阵」的组合。八种工作模式不是背出来的，而是从输入/输出两条通路推出来的：信号从哪进、经过什么、最后由哪个寄存器控制。把这一课弄透，后面按键、OLED、SPI、PWM 的引脚配置都不会再配错。

关键点：

二、八种工作模式：其实只有四条路

CubeMX 的 GPIO 模式下拉框有八项，本质是「输入/输出/复用/模拟」四类，每类再分推挽/开漏或上拉/下拉：

输入浮空（Input floating）输入外部电路外部已有上下拉的信号、USART_RX

怎么选：三句口诀

  1. 要读电平 → 输入；外部有明确电平就浮空，没有就上拉/下拉。
  2. 要驱动负载 → 推挽；要「线与」或接 5V 器件 → 开漏（外加上拉）。
  3. 信号由外设产生 → 复用；ADC 采样 → 模拟。

输出速度与驱动能力

CubeMX 里的 Maximum output speed 有 Low/Medium/High。速度越高，边沿越陡、EMI 越大；普通 LED、按键扫描用 Low 就够，SPI 高速时钟才用 High。F1 单脚最大灌/拉电流约 20mA（绝对最大 25mA），不能直接驱动电机、继电器，中间要加三极管或驱动芯片。

为什么推荐 BSRR 而不是 ODR

GPIOA->ODR |= (1 << 8);      /* 读-改-写：可能被中断打断，误改其他位 */
GPIOA->BSRR = (1 << 8);      /* 原子置位，一条指令，不会被中断拆开 */
GPIOA->BRR  = (1 << 8);      /* 原子复位 */

HAL 的 HAL_GPIO_WritePin() 内部就是写 BSRR/BRR；HAL_GPIO_TogglePin() 则是读 ODR 再写，不是原子操作，在多任务/中断里同时翻转同一引脚要加保护。

  • 重映射：比如 USART1 默认 PA9/PA10，可重映射到 PB6/PB7，需要写 AFIO_MAPR。CubeMX 里点引脚时如果出现黄色/绿色提示，说明该功能可重映射；不点重映射就直接用默认脚。

  1. 为什么 I2C 的 SDA/SCL 必须配成开漏输出，而不能用推挽？上拉电阻起什么作用？

    I2C 是多主多从的「线与」总线：任何器件都可以把线拉低，但不能主动输出高（否则两个器件一个推高一个拉低会短路大电流）。开漏输出只能拉低、释放时高阻，高电平由外部上拉电阻提供，这样多个器件「线与」才安全。上拉电阻同时决定上升沿时间，阻值太大边沿慢、通信失败，太小功耗大，常用 4.7kΩ。

  2. HAL_GPIO_TogglePin() 和 HAL_GPIO_WritePin() 在实现上有什么区别？为什么说前者不是原子的？

    WritePin 根据电平写 BSRR（置位）或 BRR（复位），是单次寄存器写，原子。TogglePin 先读 ODR 的当前位，取反后再写回 ODR，是「读-改-写」三步；如果在这之间发生中断且中断也改了同一引脚，就会丢一次翻转。多上下文共用引脚时要用 BSRR 直接写目标电平，或加临界区。

  3. 一个按键一端接 GND，另一端接 PA0。要读到「按下为 0、松开为 1」，GPIO 应该配成什么模式？如果按键一端接 3.3V，又该怎么配？

    接 GND：配「输入上拉」，松开时内部上拉到 1，按下被拉到 0。接 3.3V：配「输入下拉」，松开时内部下拉到 0，按下为 1。两种都不应配浮空，否则松开时电平不确定。若外部已有 10k 上/下拉，也可以配浮空，避免内外电阻并联改变电平。

  4. 同一引脚先被配置成 TIM2_CH1 的复用推挽，后来又被配置成普通推挽输出，会发生什么？为什么？

    后配置的会覆盖前一个：引脚输出控制从 TIM2 切回 GPIO 的 ODR，PWM 波形消失，引脚电平由 HAL_GPIO_WritePin 决定。因为复用功能本质是把输出选择器从 GPIO 切到外设，同一时刻只能有一个源驱动引脚；CubeMX 里一个引脚也只能分配一个信号，冲突时会标红。写代码时不要在两个初始化里重复配置同一脚。

一、GPIO 配置四步法

HAL 把「配一个外设」抽象成固定四步，GPIO 是最直观的例子：

第 1 步：使能时钟

F1 的 GPIO 挂在 APB2 上：

__HAL_RCC_GPIOA_CLK_ENABLE();   /* 等价于 RCC->APB2ENR |= RCC_APB2ENR_IOPAEN */
__HAL_RCC_GPIOB_CLK_ENABLE();

不使能时钟，后面写寄存器全部无效，引脚没有任何反应——这是新手第一大坑。

第 2 步：填初始化结构体

GPIO_InitTypeDef GPIO_InitStruct = {0};

GPIO_InitStruct.Pin   = GPIO_PIN_8;           /* 哪个/哪些引脚，可或运算 */
GPIO_InitStruct.Mode  = GPIO_MODE_OUTPUT_PP;  /* 输出推挽 */
GPIO_InitStruct.Pull  = GPIO_NOPULL;          /* 不用上下拉 */
GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_LOW;  /* 低速，够 LED 用 */

GPIO_InitTypeDef 只有四个成员，对应 CRL/CRH 里的 MODE/CNF 位和上下拉位。

第 3 步：调用 HAL_GPIO_Init()

HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);

第二个参数是端口基址（GPIOA…GPIOG），第一个参数里的 Pin 是 16 位掩码。一次可以初始化同一端口的多个脚：

GPIO_InitStruct.Pin = GPIO_PIN_0 | GPIO_PIN_1 | GPIO_PIN_2;

第 4 步：读写

HAL_GPIO_WritePin(GPIOA, GPIO_PIN_8, GPIO_PIN_RESET);  /* 输出低 */
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_8, GPIO_PIN_SET);    /* 输出高 */
GPIO_PinState s = HAL_GPIO_ReadPin(GPIOB, GPIO_PIN_1); /* 读输入 */
HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_8);                 /* 翻转 */

进阶版：按一下翻转，带消抖

机械按键按下/松开时会有 5–20ms 的抖动，直接读会一次按下被识别成好几次。软件消抖的通用写法是「采样 + 计时」：

#define KEY_DEBOUNCE_MS 20

static uint8_t  key_stable = 1;      /* 稳定状态：1=松开 */
static uint32_t key_tick   = 0;

void Key_Scan(void)
{
    uint8_t raw = (HAL_GPIO_ReadPin(KEY_GPIO_Port, KEY_Pin) == GPIO_PIN_RESET) ? 0 : 1;

    if (raw != key_stable) {
        if (key_tick == 0) {
            key_tick = HAL_GetTick();          /* 开始计时 */
        } else if (HAL_GetTick() - key_tick >= KEY_DEBOUNCE_MS) {
            key_stable = raw;                  /* 稳定超过 20ms，认账 */
            key_tick = 0;
            if (key_stable == 0) {             /* 下降沿：按下 */
                HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
            }
        }
    } else {
        key_tick = 0;                          /* 回到稳定态，清计时 */
    }
}

放到 while(1) 里每 1–5ms 调一次即可。硬件消抖（RC + 施密特）能省软件，但成本更高；一般产品用软件消抖就够。

本课练习 · 4 题自编 · 按课程考点

  1. 为什么 HAL_GPIO_Init() 之前必须先调用 __HAL_RCC_GPIOx_CLK_ENABLE()？只写寄存器不使能时钟会怎样？

    F1 的外设时钟默认关闭以省电，GPIO 挂在 APB2 上，RCC_APB2ENR 对应位为 0 时 GPIO 模块没有时钟，寄存器写入被忽略（读回也可能是 0），引脚保持复位后的默认状态。表现为「代码没错、就是不动」。HAL 不会替你开时钟，因为时钟管理属于 MSP 层，必须显式使能。

  2. GPIO_InitStruct.Pin 能不能一次写多个引脚？这些引脚必须满足什么条件？

    能，Pin 是 16 位掩码，如 GPIO_PIN_0 | GPIO_PIN_1。它们必须属于同一个 GPIO 端口（同一个 GPIOx），因为 HAL_GPIO_Init(GPIOx, ...) 一次只操作一个端口；不同端口的引脚要分别初始化。同一个结构体里的 Mode/Pull/Speed 会应用到所有选中的引脚。

  3. 按键接 GND、IO 配输入上拉时，为什么「按下为 0」？如果程序里写成 if (ReadPin(...) == GPIO_PIN_SET) 判断按下，会有什么现象？

    上拉使松开时 IO 通过内部电阻接到 3.3V，读到 1；按下时 IO 直接接地，读到 0。若用 == GPIO_PIN_SET 判断按下，逻辑就反了：松开时被当成按下，按下时被当成松开。现象是「不按就动作、按住反而不动」。读按键一定要结合硬件接法确认有效电平。

  4. 软件消抖为什么通常取 20ms 左右？取 1ms 或 200ms 分别有什么问题？

    机械按键的抖动一般持续 5–20ms，20ms 能覆盖大多数按键。取 1ms 太短，抖动还没结束就被当成多次按下；取 200ms 虽不误触，但按键响应明显迟钝，快速连按会丢键。具体值要看按键手册和手感，20–30ms 是常用折中；也可以用「两次采样间隔 10ms、连续两次相同才认」的写法。

基础

中断不是「更快的轮询」，而是一套由硬件仲裁的抢占机制。NVIC 决定谁先执行、谁能打断谁；HAL 把 NVIC 的寄存器封装成三个函数。优先级配反了，程序不会报错，只会「偶尔丢数据、偶尔卡死」——这一课把优先级分组、抢占与子优先级讲清楚。

一、中断体系：内核异常 + 外设中断

Cortex-M3 的「异常」分两类：

类型编号例子谁管理

二、优先级：4 位，分成「抢占」和「子优先级」

F1 的 NVIC 给每个中断 4 位优先级（0–15，数值越小越高）。这 4 位可以按不同比例分给两组：

分组抢占位数子优先级位数抢占级数子优先级级数
Group 004116
Group 11328
Group 22244
Group 33182
Group 440161

规则只有两条：

  1. 抢占优先级不同：高抢占可以打断低抢占（嵌套）；
  2. 抢占优先级相同：谁先到谁先执行，后到的等高抢占的那一个执行完再进；子优先级只在同时挂起时决定顺序，不能嵌套。

一个工程里只设置一次分组。HAL 的 HAL_Init() 默认用 NVIC_PRIORITYGROUP_4（4 位全给抢占）。如果你在别处又调了 HAL_NVIC_SetPriorityGrouping()，之前配好的优先级含义会整体变化。

三、HAL 的三个函数
/* 1. 设分组（整个工程一次，放在 main 开头或 HAL_Init 后） */
HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);

/* 2. 设某个中断的抢占/子优先级 */
HAL_NVIC_SetPriority(USART1_IRQn, 1, 0);   /* 抢占 1，子优先级 0 */

/* 3. 使能该中断 */
HAL_NVIC_EnableIRQ(USART1_IRQn);

关闭/清除挂起：

HAL_NVIC_DisableIRQ(USART1_IRQn);
HAL_NVIC_ClearPendingIRQ(USART1_IRQn);

CubeMX 的 NVIC Settings 勾选就是把这三步生成到 HAL_xxx_MspInit() 里；勾 Enable 后不要又在代码里改优先级，否则两边打架。

中断服务函数怎么写

中断里不要做的事

  • HAL_Delay()：等 SysTick，优先级不高于 SysTick 时会死等；

  • 大数组拷贝/浮点运算：拉长中断时间，影响实时性；
  • 调用不可重入函数：可能破坏主循环的状态。

正确做法：中断里只置标志/存数据，主循环处理；必须快发的用 DMA。

  1. 抢占优先级和子优先级的本质区别是什么？两个中断抢占优先级相同、子优先级不同，能互相打断吗？

    抢占优先级决定「能不能打断正在执行的中断」；子优先级只在多个中断同时挂起时决定「谁先排队」，不能打断。两个中断抢占级相同，无论子优先级如何都不能互相嵌套；先到的执行完，后到的才进。只有抢占级不同才有嵌套。

  2. HAL_NVIC_SetPriorityGrouping() 为什么建议整个工程只调用一次？如果在两个文件里分别设了 Group 2 和 Group 4 会怎样？

    分组决定 4 位优先级里「几位是抢占、几位是子优先级」，是全局解释规则。如果两处设置不同，后设置的会改变所有已配置中断的语义：原本按 Group 2 配的「抢占 1、子 2」在 Group 4 下会变成「抢占 1、无子优先级」，嵌套关系完全变化。表现是「以前能嵌套的现在不能、以前不嵌套的现在抢了」。应统一在 main 开头设一次。

  3. 为什么在优先级低于 SysTick 的中断里调用 HAL_Delay() 会卡死？如果必须延时，应该怎么做？

    HAL_Delay 靠 uwTick 递增，uwTick 由 SysTick 中断维护。如果当前中断的抢占优先级低于 SysTick，SysTick 可以打断它，uwTick 会继续走——这种情况其实不会卡死。真正卡死的是：当前中断优先级不低于 SysTick（数值 ≤ SysTick），SysTick 无法抢占，uwTick 停止增长，while 永远不满足。正确做法：中断里不要阻塞延时；用硬件定时器、状态机、或把工作放到主循环。

  4. 串口接收中断里把收到的字节追加到一个 256 字节环形缓冲区，主循环读取。需要保护哪些共享变量？怎么保护最省事？

    共享的是「写指针、读指针、缓冲区内容」。最省事的单生产者/单消费者做法：中断只写 head 和缓冲区，主循环只写 tail；两边各自只改自己的指针，用 volatile 防止优化，判断空/满用下标差值，避免同时改一个变量。若必须改同一变量，用极短的 __disable_irq()/__enable_irq() 临界区，不要在临界区里做拷贝。

基础

轮询按键要一直占着 CPU，外部中断则让硬件替你盯着引脚：电平一变，CPU 才被叫醒。F1 的 EXTI 有 20 条线，前 16 条通过 AFIO 映射到 GPIO，后 4 条接 PVD、RTC 闹钟、USB 唤醒等内部事件。这一课把「引脚 → EXTI → NVIC → 回调」整条链走通。

一、EXTI 的路径：从引脚到 CPU
PA0 ─┐
PB0 ─┼─► AFIO 选择 ─► EXTI0 ─► 边沿检测 ─► NVIC ─► CPU
PC0 ─┘   （选一个）              （上升/下降/双边）

关键点：

  • EXTI0–EXTI15 与 GPIO 的 Px0–Px15 一一对应：EXTI0 只能接某个端口的第 0 脚，不能接 PA1；
  • 同一编号只能选一个端口：PA0、PB0、PC0 都能连到 EXTI0，但 AFIO 的 EXTI0[3:0] 只能选其中一个。想同时监控 PA0 和 PB0，必须用 EXTI0 + EXTI1（不同编号）；
  • EXTI16–EXTI19 不经过 GPIO/AFIO，直接来自 PVD、RTC 闹钟、USB 唤醒、以太网唤醒；
  • AFIO 时钟必须使能（__HAL_RCC_AFIO_CLK_ENABLE()），否则映射不生效。CubeMX 会自动加。

边沿与挂起

EXTI 的每个通道有：

  • 触发选择：上升沿 / 下降沿 / 双边沿；
  • 屏蔽位：屏蔽后不产生请求；
  • 挂起位：事件发生后置 1，进中断后必须软件写 1 清除，否则会反复进中断（或不再进）。

HAL 的 HAL_GPIO_EXTI_IRQHandler() 已经帮你判挂起位并清除，用户回调里不用再清。

三、写回调：只做轻量事
/* main.c — USER CODE BEGIN 4 */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == KEY_Pin) {
        static uint32_t last = 0;
        uint32_t now = HAL_GetTick();
        if (now - last < 20) return;        /* 20ms 内重复触发视为抖动 */
        last = now;

        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    }
}

要点：

  • 回调的入参是「哪条 EXTI 线」，多个引脚共用回调时用 if 区分；
  • 中断里只翻转/置标志，复杂逻辑留给主循环；
  • 用时间戳做消抖，比在中断里 HAL_Delay 安全得多（中断里不能长等）；
  • 如果按键接 3.3V，应配 GPIO_MODE_IT_RISING + 下拉。
四、实战：红外对管计数

对射式红外传感器的 DO 输出在遮挡时会产生下降沿。把 DO 接 PB14，配 GPIO_EXTI14 下降沿、上拉，回调里计数：

volatile uint32_t ir_count = 0;

void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == GPIO_PIN_14) {
        ir_count++;                 /* volatile：主循环会读 */
    }
}

主循环每秒打印一次，用 printf 或 OLED 显示。注意 ir_count 是 32 位，主循环读它时如果中断也在写，单次 32 位读在 M3 上是原子的（对齐访问），但 ir_count++ 不是；只让中断写、主循环读，就不要在主循环里自增。

  1. 为什么 PA0 和 PB0 不能同时作为外部中断源？如果两个按键都需要中断，应该怎么接？

    因为两者都映射到同一条 EXTI0，而 AFIO 的 EXTI0 选择器只能选一个端口（PA/PB/PC…）。两个同时接，只有一个能进 EXTI。解决：把其中一个按键换到别的编号，例如 PA0→EXTI0、PB1→EXTI1；或者不用 EXTI，改用定时器轮询/矩阵扫描。

  2. HAL_GPIO_EXTI_IRQHandler() 内部做了哪几件事？如果用户直接在 EXTI1_IRQHandler() 里写业务而不调用它，会有什么后果？

    它先检查该引脚对应的 EXTI 挂起位是否置位，若置位则清除挂起位，然后调用 HAL_GPIO_EXTI_Callback(GPIO_Pin)。如果绕过它，挂起位不会被清除，NVIC 会认为中断仍有效，退出后立刻再次进入，表现为「中断风暴」把主程序饿死；同时 HAL 的回调也不会被调用。

  3. 按键接 GND、配下降沿触发，但按下时读到的是低电平。为什么「按下」对应下降沿？如果按键接 3.3V，应该配什么边沿？

    接 GND + 上拉时，松开为高、按下变低，电平从高到低的跳变就是下降沿，所以配下降沿。接 3.3V + 下拉时，松开为低、按下变高，对应上升沿。边沿选反的现象是「松开时触发、按下不触发」。

  4. 在 EXTI 回调里调用 printf 打印按键次数，为什么可能丢数据或死机？应该怎么改？

    printf 通过 HAL_UART_Transmit 阻塞发送，一个短字符串也要几十微秒到几毫秒；期间同优先级/低优先级中断被挂起，串口自己的接收中断也可能丢字节。若串口中断优先级低于按键中断，还会互相拖。改法：回调里只 count++ 或置标志，主循环统一打印；要高频日志用环形缓冲 + DMA 发送。

基础

串口是单片机最便宜、最通用的通信口：两根线、不需要时钟线，靠双方约定好的波特率同步。它也是最好的调试工具——printf 能看见，排查外设就成功了一半。这一课从一帧数据的形状讲到 F1 的 USART 框图，最后把波特率算到寄存器。

读完这一课你能做到

  • 能画出一帧 8-N-1 的波形，指出起始位、数据位、校验位、停止位
  • 能说清 USART 的发送/接收移位寄存器、DR、SR、BRR 各自的作用
  • 能独立算出 72MHz 下 9600/115200 的 BRR 值，并解释误差从哪来
  • 能区分 TTL 串口与 RS-232 电平，知道为什么要 MAX3232
一、一帧数据长什么样

UART 异步通信没有时钟线，双方靠「起始位」对齐，然后按波特率逐位采样。8 位数据、无校验、1 停止位（8-N-1）的一帧是 10 位：

空闲(高)  起始  D0  D1  D2  D3  D4  D5  D6  D7  停止  空闲
────────┐    ┌──┬──┬──┬──┬──┬──┬──┬──┐    ┌────────
        └────┘  │  │  │  │  │  │  │  └────┘
         0     1  0  1  0  0  1  1  1
  • 空闲为高，起始位是 1 位低电平；
  • 数据低位在前（LSB first）；
  • 校验位可选（奇/偶）；
  • 停止位 1/1.5/2 位高电平；
  • 波特率 = 每秒传输的位数。115200 时一位约 8.68µs，一帧 10 位约 86.8µs。

接收方在起始位下降沿后，按 16 倍频采样，在第 8、9、10 个采样点做多数表决，所以能容忍一定的波特率误差（通常 < 3%）。

三、波特率：从公式到 BRR

F1 的 USART 波特率公式（过采样 16）：

USARTDIV = fCK / (16 × BaudRate)
BRR = (整数部分 << 4) | (小数部分 × 16 四舍五入)

以 72MHz、115200 为例：

USARTDIV = 72,000,000 / (16 × 115200) = 39.0625
整数 39 = 0x27，小数 0.0625 × 16 = 1
BRR = 0x271

9600：

USARTDIV = 72,000,000 / (16 × 9600) = 468.75
整数 468 = 0x1D4，小数 0.75 × 16 = 12 = 0xC
BRR = 0x1D4C

HAL 不需要你算：huart1.Init.BaudRate = 115200; 后 HAL_UART_Init() 会按 HAL_RCC_GetPCLK2Freq() 自动写 BRR。但你要知道它依赖 PCLK2：USART1 挂 APB2（72MHz），USART2/3 挂 APB1（36MHz）。时钟改错，BRR 就错，输出全是乱码。

2% 以内可接受通常能通信
3% 左右临界偶发误码，长帧更明显
> 5%不可用全是乱码

  1. 8-N-1、115200 波特率下，传输 100 字节需要多长时间？如果把停止位改成 2 位，时间变成多少？

    8-N-1 一帧 10 位（1 起始 + 8 数据 + 1 停止），100 字节 = 1000 位，115200 bps 下约 1000/115200 ≈ 8.68ms。2 停止位时一帧 11 位，100 字节 = 1100 位 ≈ 9.55ms。实际还要加上软件处理与帧间空隙。

  2. 72MHz、USART1、目标波特率 115200，BRR 应该是多少？如果误把 USART1 的时钟按 36MHz 算，会怎样？

    USARTDIV = 72e6/(16×115200) = 39.0625，BRR = 0x271。如果按 36MHz 算，USARTDIV ≈ 19.53，BRR 约 0x139，实际波特率只有目标的一半（约 57600），与电脑的 115200 不匹配，收到的是乱码。USART1 挂 APB2，不能用 PCLK1 算。

  3. 为什么 UART 不需要时钟线也能正确采样？它对双方时钟误差的容忍度为什么大约是 3%？

    接收方用起始位的下降沿重置内部采样计数器，然后按约定的 16 倍波特率计数，在每位中间采样；每帧起始都会重新对齐，所以不需要共享时钟。误差容忍度来自「一帧 10 位、采样点在第 8–10 个 16 分频点」：若双方累计偏差在一帧内超过约半个位，采样就会落到相邻位，通常允许 2–3%（10 位帧，最后一位的累计误差最大）。

  4. 串口接收中断里只读了一个字节，但主循环处理很慢，会发生什么？如何用最简单的方式避免？

    USART 的 DR 只有一级缓冲，下一字节到来前没读走就置 ORE（溢出），新数据覆盖旧数据，表现为丢字节。最简单：接收中断里立刻把字节存入环形缓冲区（只做搬运，几十个周期），主循环慢慢处理；或者用 DMA 把数据直接搬到内存，CPU 只在空闲中断时批量处理。不要在高优先级中断里做耗时解析。

四、实战 2：不定长数据——空闲中断 + DMA

思路

DMA 把串口数据连续搬到缓冲区；一帧数据发完，总线会空闲，触发 IDLE 中断；在 IDLE 回调里算出「这次收了多少字节」，交给主循环解析，然后重新启动 DMA。

#define RX_SIZE 128
uint8_t  rx_buf[RX_SIZE];
uint16_t rx_len = 0;
volatile uint8_t rx_flag = 0;

/* 启动：DMA 接收 + 开空闲中断 */
void UART_StartRx(void)
{
    HAL_UART_Receive_DMA(&huart1, rx_buf, RX_SIZE);
    __HAL_UART_ENABLE_IT(&huart1, UART_IT_IDLE);
}

/* 空闲中断处理：HAL 没有现成回调，需要自己判 */
void USART1_IRQHandler(void)
{
    HAL_UART_IRQHandler(&huart1);

    if (__HAL_UART_GET_FLAG(&huart1, UART_FLAG_IDLE)) {
        __HAL_UART_CLEAR_IDLEFLAG(&huart1);

        /* 停 DMA，读剩余计数算出已收字节数 */
        HAL_UART_DMAStop(&huart1);
        rx_len = RX_SIZE - __HAL_DMA_GET_COUNTER(huart1.hdmarx);
        rx_flag = 1;

        HAL_UART_Receive_DMA(&huart1, rx_buf, RX_SIZE);  /* 重新挂 */
        __HAL_UART_ENABLE_IT(&huart1, UART_IT_IDLE);
    }
}

/* 主循环解析 */
if (rx_flag) {
    rx_flag = 0;
    rx_buf[rx_len] = '\0';          /* 预留 1 字节给结束符 */
    printf("recv %u bytes: %s\r\n", rx_len, rx_buf);
}

要点

  • 缓冲区留 1 字节给 '\0'，RX_SIZE-1 更安全；
  • HAL_UART_DMAStop() 会同时关收发，若还要发，改用 HAL_UART_AbortReceive() 或只停 RX 流；
  • IDLE 标志清除必须用 __HAL_UART_CLEAR_IDLEFLAG（读 SR 再读 DR 的序列），普通清标志不行；
  • 数据量大时用双缓冲/环形 DMA，避免解析期间新数据覆盖。

  1. HAL_UART_Transmit、HAL_UART_Transmit_IT、HAL_UART_Transmit_DMA 三者的返回时机有什么不同？分别在什么场景用？

    阻塞版在数据全部发完（或超时）才返回，期间 CPU 空转；中断版把缓冲区地址交给外设后立即返回，每发一个字节进一次中断，全部发完调 TxCpltCallback；DMA 版也是立即返回，但由 DMA 控制器搬运，CPU 完全不参与，完成时进回调。初始化打印/少量调试用阻塞；中等长度、要并行处理用中断；大批量、高吞吐用 DMA。

  2. 为什么 HAL_UART_Receive_IT(&huart1, &rx, 1) 只能收一个字节？要连续接收有哪几种改法？

    因为 HAL 的接收状态机把「接收长度」作为一次传输的参数，收满指定长度就结束并回调，不会自动续传。改法：① 在 RxCpltCallback 里再次调用 Receive_IT（最常用）；② 一次挂一个较大缓冲区，收满再处理（定长协议）；③ 用 DMA + IDLE 做不定长；④ 用 DMA Circular 模式持续搬运，主循环按写指针取数据。

  3. 「空闲中断 + DMA」方案里，rx_len = RX_SIZE - __HAL_DMA_GET_COUNTER(...) 的含义是什么？为什么必须先停 DMA？

    DMA 的计数器从设定长度开始递减，剩余计数 = 还没搬的字节数，所以「总长度 − 剩余」就是本次已收字节数。先停 DMA 是为了冻结计数器和缓冲区：如果不停，CPU 读计数与后续数据到达之间存在竞争，算出的长度可能偏大/偏小，且重新启动 DMA 会重置计数器。停完再算、再重启，得到的是稳定的一帧长度。

  4. 串口中断里调用 printf 会有什么问题？如果调试时确实想在中端里打日志，应该怎么设计？

    printf 内部走阻塞发送，一个几十字节的字符串要几毫秒；期间同优先级/低优先级中断被挂起，串口接收可能溢出，系统实时性崩坏。更糟的是 printf 不可重入，主循环和中断同时调用会破坏内部状态。正确设计：中断里只把日志写入环形缓冲区（或只置事件），主循环/DMA 负责真正发送；或者用 HAL_UART_Transmit_IT 发到独立缓冲，绝不在中断里等。

hiwdg.Instance       = IWDG;

hiwdg.Init.Reload    = 1250;                /* 约 2s */

    Error_Handler();
}

HAL_IWDG_Refresh(&hiwdg);

**HAL_IWDG_Init() 一调用，看门狗立刻开始计数**，没有「先关后开」的窗口；初始化后必须尽快进入喂狗循环。

正确喂狗的位置

while (1)
{
    Task_Sensor();       /* 采集 */
    Task_Comm();         /* 通信 */
    Task_Display();      /* 显示 */

    /* 只有前面都跑完，才喂狗 */
    HAL_IWDG_Refresh(&hiwdg);
    HAL_Delay(10);
}

不要放在定时器中断里无条件喂——那样主循环卡死，中断还在喂，看门狗形同虚设。也不要放在 HAL_Delay 之前，否则延时卡住时狗已经喂过了。

二、WWDG：窗口看门狗

与 IWDG 的区别

项目IWDGWWDG
时钟源LSI ~40kHz（独立）PCLK1（36MHz，依赖主时钟）

WWDG 的计数器是 7 位，减到 0x40 时如果还没喂，就会复位；同时有一个「窗口值」W，计数器高于 W 时喂狗也会复位。所以喂狗必须落在 [0x40, W] 这个窗口里。

0x7F ────────► W ────────► 0x40 ──► 0x3F 复位
     不能喂        可喂        必须已喂

超时与窗口计算

WWDG 的超时（从 0x7F 减到 0x40）：

T = 4096 × 2^WDGTB × (0x3F + 1) / PCLK1

PCLK1=36MHz、WDGTB=3（÷8）时：T = 4096×8×64/36e6 ≈ 58.3ms。窗口值 W 决定最早能喂的时刻：W 越接近 0x7F，窗口越窄。

HAL 配置

WWDG_HandleTypeDef hwwdg;

hwwdg.Instance       = WWDG;
hwwdg.Init.Prescaler = WWDG_PRESCALER_8;
hwwdg.Init.Window    = 0x50;     /* 窗口值：计数器 > 0x50 时喂会复位 */
hwwdg.Init.Counter   = 0x7F;
hwwdg.Init.EWMode    = WWDG_EWI_DISABLE;

if (HAL_WWDG_Init(&hwwdg) != HAL_OK) Error_Handler();

/* 主循环在窗口内喂 */
HAL_WWDG_Refresh(&hwwdg);

HAL_WWDG_Init() 也会立刻启动。喂太早会复位，所以主循环的周期必须落在窗口内；周期波动大的系统不要用 WWDG。

  1. IWDG 的 LSI 是 40kHz，预分频 64、重装载 1250，溢出时间是多少？如果 LSI 实际是 30kHz，实际时间变成多少？

    标称：T = 64 × 1251 / 40000 ≈ 2.0s。若 LSI 降到 30kHz：T = 64 × 1251 / 30000 ≈ 2.67s。也就是说 LSI 偏慢时超时变长，偏快时变短；设计上要按最坏情况留余量，别把喂狗周期卡在超时边缘。

  2. 为什么说「在定时器中断里喂狗」等于没开看门狗？正确的喂狗条件是什么？

    因为看门狗要检测的是「主循环/关键任务是否还活着」。定时器中断由硬件独立触发，即使主循环卡死（死循环、阻塞、HardFault 前的假活），中断仍会按时喂狗，硬件永远不复位。正确做法：主循环跑完所有关键任务后喂一次；或用「任务打卡」机制，只有所有任务都置了标志才喂。

  3. WWDG 的「窗口」到底限制了什么？如果一个任务的周期在 10–100ms 之间波动，适合用 WWDG 吗？

    窗口限制了「最早能喂的时刻」：计数器高于 Window 值时喂狗会立即复位，低于 0x40 也会复位，只有落在窗口内才合法。它抓的是「程序跑太快/跳过某段代码」。周期在 10–100ms 大幅波动的任务不适合 WWDG：周期短于窗口下沿会喂太早复位，长于超时会喂太晚复位；这种系统用 IWDG 更稳。

  4. 产品从调试版切到发布版，看门狗相关要做哪些检查？

    ① 确认 HAL_IWDG_Init() 在发布版一定被调用（不要被调试宏关掉）；② 喂狗点覆盖所有关键任务，且不会被长时间阻塞（Flash 擦写、长延时、网络等待）；③ 超时留足余量（至少 2 倍最坏循环时间）；④ 启动时读取并清除复位标志，记录复位原因；⑤ 低功耗模式与看门狗的关系确认（待机时 IWDG 仍在跑，唤醒方式要设计好）；⑥ 用长时间老化测试验证不会误复位。

基本定时器与定时中断第四篇 · 定时器与看门狗

基础

定时器是单片机里最「值钱」的外设：它不占 CPU、精度高、还能衍生出 PWM、输入捕获、编码器。F1 的基本定时器 TIM6/TIM7 功能最少，正好用来把「预分频 → 计数 → 溢出 → 中断」这条链讲清楚，后面通用/高级定时器都是在这条链上加功能。

  • 能用 CubeMX + HAL 配出 1ms/1s 定时中断，在回调里做心跳
  • 能区分「更新中断」与「更新事件」，知道预装载（ARPE）的作用
一、基本定时器里有什么

TIM6/TIM7 的结构极简：

内部时钟 CK_INT（72MHz）
   │
   ▼
┌─────────┐   ┌─────────┐   ┌─────────┐
│  PSC    │──►│  CNT    │──►│  ARR    │──► 更新事件 UE
│ 预分频  │   │ 计数器  │   │ 自动重装│      ├─ 更新中断 UIE
└─────────┘   └─────────┘   └─────────┘      └─ 触发 DAC/ADC
寄存器作用16 位范围
PSC把 72MHz 分频成计数时钟0–65535（实际 ÷(PSC+1)）
CNT当前计数值，自动递增0–65535
ARR计到多少溢出并重装0–65535

计数时钟：

fCNT = fCK / (PSC + 1)

溢出周期：

T = (PSC + 1) × (ARR + 1) / fCK

以 72MHz、1ms 为例：取 PSC=71（→1MHz），ARR=999（→1000 个数）→ T = 1000/1MHz = 1ms。

以 72MHz、1s 为例：PSC=7199（→10kHz），ARR=9999（→10000 个数）→ T = 1s。

16 位上限：单靠 PSC/ARR 最大定时 = 65536×65536/72e6 ≈ 59.6s。要更长，用「定时中断里再计数」的软件分频。

二、更新事件与预装载
  • 更新事件（UE）：CNT 从 ARR 回到 0 时产生，可以触发中断、DMA、DAC；
  • 更新中断（UIE）：UE 使能到 NVIC 的那一路；
  • ARPE（自动重装载预装载）：置 1 时，写 ARR 先写入影子寄存器，等下一次更新才生效，避免运行中改周期产生毛刺。CubeMX 默认开启。

上电第一次计数也会产生一次更新事件（因为要装载 ARR/PSC），这就是「定时器一开就多进一次中断」的原因。处理办法：启动前先 __HAL_TIM_CLEAR_FLAG(&htim6, TIM_FLAG_UPDATE)，或第一次中断里忽略。

三、CubeMX 配置
  1. Timers → TIM6：Clock Source 选 Internal Clock；
  2. Parameter Settings：
  • Prescaler = 71
  • Counter Mode = Up
  • Counter Period = 999
  • auto-reload preload = Enable
  1. NVIC Settings：勾 TIM6 global interrupt；
  2. 生成后 tim.c 里有 MX_TIM6_Init()。
四、HAL 代码：启动与回调

/* USER CODE BEGIN 2 */
HAL_TIM_Base_Start_IT(&htim6);      /* 启动计数 + 开更新中断 */
/* USER CODE END 2 */

/* USER CODE BEGIN 4 */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM6) {
        static uint32_t ms = 0;
        ms++;
        if (ms % 1000 == 0) {
            HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);   /* 每 1s 翻转 */
        }
    }
}
/* USER CODE END 4 */

注意：

  • HAL_TIM_Base_Start_IT() 才会开中断；只调 HAL_TIM_Base_Start() 不会进回调；
  • HAL_TIM_PeriodElapsedCallback() 是所有定时器共用的弱函数，多个定时器要用 htim->Instance 区分；
  • 回调里只做计数/置标志，耗时逻辑放主循环。

  1. 72MHz、PSC=7199、ARR=9999 时，定时周期是多少？如果想得到 500ms，保持 PSC 不变，ARR 应该是多少？

    T = (7199+1)×(9999+1)/72e6 = 7200×10000/72e6 = 1s。500ms 时保持 PSC=7199（10kHz），需要 5000 个数，ARR = 4999。注意 ARR 是「计到该值溢出」，所以计数个数 = ARR+1。

  2. 为什么 TIM2/3/4 挂 APB1（36MHz），但算 PWM 周期时却用 72MHz？基本定时器 TIM6/7 也这样吗？

    F1 的规则：APB 预分频≠1 时，定时器时钟 = PCLK×2。APB1 是 ÷2（36MHz），所以 TIM2/3/4 的计数时钟是 72MHz。TIM6/7 也挂 APB1，同样享受 ×2，也是 72MHz。只有 I2C、USART2/3 等非定时器外设按 36MHz 算。CubeMX 的时钟树会用橙色标出定时器时钟，可以直接看到。

  3. 更新中断和更新事件有什么区别？只想触发 ADC 而不进中断，应该怎么配？

    更新事件是定时器内部信号（UE），可以由 CNT 溢出产生；更新中断是把这个事件送到 NVIC（UIE 位）。触发 ADC/DAC 用事件（TRGO 输出），不需要开 UIE，也不需要在 NVIC 里使能；开 UIE 会多一次中断开销。CubeMX 里在 TIM 的 Trigger Output (TRGO) 选 Update Event，ADC 里选对应的外部触发源。

  4. 定时器中断里执行 HAL_Delay(1) 会发生什么？为什么定时器中断里不能做耗时操作？

    HAL_Delay 等 SysTick；如果 TIM 中断优先级高于 SysTick，SysTick 无法抢占，uwTick 停止，程序永远卡在中断里，主循环和看门狗都停。即便优先级低于 SysTick，中断里阻塞 1ms 也会让其他中断延迟、定时抖动。定时器中断应只做计数、置标志、翻转 IO，耗时处理交给主循环。

基础

PWM 是「用数字口输出模拟效果」的万能工具：调 LED 亮度、控舵机角度、调电机转速，都是同一件事——固定频率，改占空比。F1 的通用定时器 TIM2/3/4 每个都有 4 个通道，配好时基再配通道，就能输出 4 路独立 PWM。

  • 能用 CubeMX + HAL 输出 PWM，并用 __HAL_TIM_SET_COMPARE 动态调节

一、PWM 是怎么产生的

通用定时器的输出比较部分：

CNT（计数） ──► 比较器 ◄── CCR（比较值）
                  │
                  ▼
             OCxREF ──► 输出模式/极性 ──► 引脚
  • PWM 模式 1：CNT < CCR 时输出有效电平，否则无效；
  • PWM 模式 2：反过来，CNT < CCR 时无效；
  • 有效电平由极性（高/低）决定，CubeMX 里 CH Polarity 选 High 就是高电平有效。

频率与占空比：

fPWM = fCK / ((PSC + 1) × (ARR + 1))
占空比 = CCR / (ARR + 1)

以 72MHz、1kHz 为例：PSC=71（→1MHz）、ARR=999（→1kHz），CCR=300 时占空比 30%。

二、CubeMX 配置
  1. Timers → TIM2：Clock Source = Internal Clock；
  2. Channel1 选 PWM Generation CH1；
  3. Parameter Settings：
  • Prescaler = 71
  • Counter Period = 999
  • Pulse = 0（初始占空比 0）
  • CH Polarity = High
  1. 引脚图确认 PA0 被分配给 TIM2_CH1；
  2. 生成后 tim.c 有 MX_TIM2_Init()。

通道与引脚是绑定的：TIM2_CH1 可以是 PA0/PA15，TIM2_CH2 是 PA1/PB3，TIM3_CH1 是 PA6/PB4。CubeMX 点通道时会显示可用脚，选一个没被占用的。

三、HAL 代码：启动与调占空比

TIM_HandleTypeDef htim2;

/* USER CODE BEGIN 2 */
HAL_TIM_PWM_Start(&htim2, TIM_CHANNEL_1);     /* 启动通道 1 的 PWM */
/* USER CODE END 2 */

/* USER CODE BEGIN 3 */
for (uint16_t i = 0; i <= 1000; i += 10) {
    __HAL_TIM_SET_COMPARE(&htim2, TIM_CHANNEL_1, i);   /* 改 CCR */
    HAL_Delay(10);
}
/* USER CODE END 3 */

调占空比的三种写法：

__HAL_TIM_SET_COMPARE(&htim2, TIM_CHANNEL_1, 300);   /* 直接写 CCR */

HAL_TIM_PWM_Start(&htim2, TIM_CHANNEL_1);            /* 只启动，不改变 CCR */

四、实战 1：呼吸灯

{

  2. PWM 模式 1 和模式 2 的区别是什么？如果 LED 是低电平点亮，CH Polarity 应该怎么设？

  4. 运行中直接改 htim2.Instance->CCR1 与 __HAL_TIM_SET_COMPARE 有区别吗？为什么建议开 CCR 预装载？

    两者最终都是写 CCR1 寄存器，效果相同（宏只是加类型转换/可读性）。区别在预装载：开了 OCxPE 后，写 CCR 只是写预装载寄存器，真正生效在下一个更新事件，避免在一个 PWM 周期中间改值造成窄脉冲/毛刺；不开则立即生效，可能在当前周期产生一个异常占空比。动态调光/调速建议开预装载。

进阶

PWM 是「定时器往外发」，输入捕获是「定时器往里量」：引脚上的边沿一到，硬件立刻把当前 CNT 抄进 CCR，误差只有一个计数周期。用它测频率、测脉宽、测占空比，比软件轮询准得多，也不占 CPU。

  • 能用 CubeMX + HAL 配出捕获中断，在回调里读 CCR

一、捕获通路
引脚 ─► 输入滤波 ─► 边沿检测 ─► 捕获事件 ─► CCRx = CNT
                                      │
                                      └─► 捕获中断 CCxIE
  • 每个通道有一个 CCR，捕获发生时硬件把 CNT 复制进去；
  • 可以选上升沿、下降沿或双边沿；
  • 输入滤波（IC Filter）能滤掉窄脉冲，但会引入延迟；
  • 捕获不会停计数器，CNT 继续跑，所以两次捕获的差值就是时间。

测周期与占空比

两次上升沿之间的差值 ΔT = (CCR2 - CCR1)（或加溢出补偿）
频率 = 1 / (ΔT × 计数周期)
高电平时间 = 下降沿捕获值 - 上升沿捕获值
占空比 = 高电平时间 / 周期

计数周期 = (PSC+1)/72MHz。例如 PSC=71，计数周期 1µs；ΔT=1000 → 1ms → 1kHz。

四、测占空比：一个通道 + 双边沿

{

    uint32_t v = HAL_TIM_ReadCapturedValue(htim, TIM_CHANNEL_1);
    if (state == 0) {          /* 上升沿 */
        rise = v;
        state = 1;
        __HAL_TIM_SET_CAPTUREPOLARITY(htim, TIM_CHANNEL_1, TIM_INPUTCHANNELPOLARITY_FALLING);
    } else {                   /* 下降沿 */
        fall = v;
        state = 0;
        __HAL_TIM_SET_CAPTUREPOLARITY(htim, TIM_CHANNEL_1, TIM_INPUTCHANNELPOLARITY_RISING);

        uint32_t high = fall - rise;
        /* 需要下一次上升沿才能得到周期，这里只算高电平 */
    }
}

五、溢出：低频测量绕不过去的坑

CNT 是 16 位，1MHz 计数时最大 65.535ms；信号低于约 15Hz，两次捕获之间 CNT 会溢出（从 65535 回到 0），直接相减会得到错误的小值。

处理办法：

  • 在更新中断里累计溢出次数：

{
    if (htim->Instance == TIM3) overflow++;
}

/* 计算周期：加上溢出补偿 */
period_us = (now - last_capture) + overflow * 65536U;
  • 或者降低计数时钟（PSC 加大），牺牲分辨率换量程；
  • 高频信号则相反：PSC 调小、提高分辨率。

  2. 为什么输入捕获测频率比「定时器中断里软件计数」更准？

    捕获是硬件在边沿瞬间把 CNT 复制到 CCR，误差只来自计数时钟（±1 个计数周期），不受中断延迟影响；软件计数依赖中断响应，中断被高优先级任务拖延时就会漏计/多计，信号频率越高误差越大。捕获适合高频、精确测量，软件计数适合低频、粗略统计。

  4. 捕获回调里读 CCR 之后，为什么还要考虑「下一次捕获已经把 CCR 覆盖」的问题？应该怎么读最稳？

    CCR 只有一份，新的捕获会立刻覆盖旧值；如果回调执行慢，可能读到的是下一次的值。最稳的是在回调里第一时间读 HAL_TIM_ReadCapturedValue()（它读 CCR），并保证回调足够短；多通道共享时用 htim->Channel 区分；不要在回调里做 printf/长运算。必要时用 DMA 把 CCR 搬到内存（F1 的捕获 DMA 支持有限，通常还是靠短回调）。

难点

高级定时器 TIM1 比通用定时器多了三样「电机/电源专用」的功能：重复计数器（发指定个数脉冲）、互补输出（一对反相 PWM）、死区与刹车（防止上下桥臂直通）。它们是三相电机、H 桥、逆变器的核心，也是定时器里最容易配错的部分。

一、重复计数器：指定个数 PWM

通用定时器的更新事件是「每个周期一次」；TIM1 多了一个 RCR（Repetition Counter）：

每次溢出 → RCR 减 1 → 只有 RCR 减到 0 才产生更新事件，并重装 RCR

所以更新频率 = PWM 频率 / (RCR + 1)。它的典型用途：

  • 让更新中断/ADC 触发按 N 个 PWM 周期发生一次，降低中断频率；
  • 配「单脉冲模式」输出精确个数：RCR = N−1，再配合 One Pulse Mode，发完 N 个脉冲自动停。

CubeMX 配置（TIM1，PA8/PA7）

  1. TIM1 → Channel1: PWM Generation CH1；
  2. Parameter Settings：
  • Prescaler = 71，Counter Period = 999（1kHz）
  • Repetition Counter = 9（每 10 个周期一次更新）
  • One Pulse Mode 视需求开启；
  1. NVIC 勾 TIM1 update interrupt（若用中断计数）。
/* 启动后，每 10 个 PWM 周期进一次更新中断 */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM1) {
        pulses_done += 10;
        if (pulses_done >= 100) {          /* 发满 100 个脉冲 */
            HAL_TIM_PWM_Stop(&htim1, TIM_CHANNEL_1);
        }
    }
}

精确个数最好用硬件「单脉冲 + RCR」，软件计数会被中断延迟影响；软件法只适合对个数要求不严的场合。

二、互补输出：一对反相 PWM

TIM1 的每个通道都有 CHx 和 CHxN 两个输出：

CH1  ─────┐        ┌────
          └────────┘
CH1N       ┌────────┐
      ─────┘        └────
          死区  死区
  • CH1 与 CH1N 反相；
  • 两者之间插入死区，保证上下桥臂不会同时导通（直通会烧 MOS）；
  • 互补输出必须使能 MOE（主输出使能），HAL 在 HAL_TIM_PWM_Start 时会处理。

CubeMX 配置

  1. TIM1 → Channel1 选 PWM Generation CH1 CH1N；
  2. Parameter Settings：
  • Dead Time 填 DTG 值（见下一节）
  • Automatic Output State = Enable
  • Break State 按需；
  1. 引脚：PA8（CH1）、PB13（CH1N）；
  2. 生成后先 HAL_TIM_PWM_Start(&htim1, TIM_CHANNEL_1)，再 HAL_TIMEx_PWMN_Start(&htim1, TIM_CHANNEL_1)。
HAL_TIM_PWM_Start(&htim1, TIM_CHANNEL_1);       /* CH1 */
HAL_TIMEx_PWMN_Start(&htim1, TIM_CHANNEL_1);    /* CH1N */
__HAL_TIM_SET_COMPARE(&htim1, TIM_CHANNEL_1, 500);

只启动 PWM_Start 不启动 PWMN_Start，互补脚不会输出——这是「CH1 有波形、CH1N 没波形」的最常见原因。

三、死区时间：DTG 怎么算

死区由 BDTR 的 DTG[7:0] 编码，F1 的规则（tDTS = 1/72MHz ≈ 13.9ns）：

DTG[7:5]公式范围
0xxDTG[7:0] × tDTS0–127 × 13.9ns ≈ 0–1.76µs
10x(64 + DTG[5:0]) × 2 × tDTS1.78–3.52µs
110(32 + DTG[4:0]) × 8 × tDTS3.56–7.04µs
111(32 + DTG[4:0]) × 16 × tDTS7.12–14.08µs

例：要 1µs 死区 → 1µs / 13.9ns ≈ 72 → DTG = 72（0x48）。

HAL 里直接填 DTG 值：

htim1.Init.DeadTime = 72;     /* 约 1µs */

死区不是越大越好：太小防不住直通，太大会让输出波形失真、有效电压下降。按 MOS 的关断时间 + 驱动延迟留 20–50% 余量。

四、刹车（BKIN）：紧急关断

刹车输入（BKIN）一旦有效，硬件立刻把 CHx/CHxN 拉到安全电平（可配空闲态），并置刹车标志，不需要 CPU 参与。典型用于过流保护：

/* 刹车引脚 PB12，高电平有效 */
htim1.Init.BreakState = TIM_BREAK_ENABLE;
htim1.Init.BreakPolarity = TIM_BREAKPOLARITY_HIGH;
htim1.Init.AutomaticOutput = TIM_AUTOMATICOUTPUT_ENABLE;

/* 刹车中断里处理 */
void HAL_TIMEx_BreakCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM1) {
        motor_stop();
        printf("BREAK! check over-current\r\n");
    }
}

刹车后要恢复输出，必须清刹车标志并重新使能 MOE（__HAL_TIM_MOE_ENABLE），HAL 的 HAL_TIMEx_ConfigBreakDeadTime() 可重配。

PWM 输入模式第四篇 · 定时器与看门狗

P110 – P113　·　6 节　·　4 题

难点

用输入捕获测占空比要来回切极性，麻烦且容易漏边沿。PWM 输入模式把这件事交给硬件：一个通道测周期（上升沿到上升沿），另一个通道测高电平（上升沿到下降沿），两个 CCR 同时就绪，读一次就能算出频率和占空比。它是读遥控接收机、转速传感器、PWM 型编码器最省事的办法。

  • 能在回调里用 CCR1/CCR2 算出频率与占空比
一、原理：一个引脚，两路捕获

PWM 输入模式的核心是「信号同时送到两个捕获通道」：

TI1（引脚） ──► IC1 ──► 上升沿捕获 ──► CCR1（周期）
           └──► IC2 ──► 下降沿捕获 ──► CCR2（高电平）
                    ▲
       从模式复位：上升沿把 CNT 清零

配合 从模式复位（Slave Mode Reset）：每个上升沿把 CNT 归零，于是

CCR1 = 一个完整周期的计数值
CCR2 = 高电平持续的计数值
频率 = 计数时钟 / CCR1
占空比 = CCR2 / CCR1

两次捕获由硬件同时完成，不存在「软件切极性漏边沿」的问题。

二、CubeMX 配置（TIM3_CH1 / PA6）
  1. TIM3 → Channel1 选 **PWM Input on CH1**（不是 Input Capture direct）；
  2. Parameter Settings 会自动填好：
  • Prescaler = 71（1MHz）
  • Counter Period = 65535
  • IC1 Polarity = Rising，IC2 Polarity = Falling
  • IC1 Selection = Direct，IC2 Selection = Indirect
  • Slave Mode = Reset Mode
  • Trigger Source = TI1FP1
  1. NVIC 勾 TIM3 global interrupt；
  2. 生成后 MX_TIM3_Init() 已经配好两路 IC 与从模式。

不要手动改 IC2 的极性/选择，PWM Input 模式依赖「IC2 间接映射到 TI1」这一组固定配置；改一处就可能只剩一路捕获。

四、量程与分辨率
参数影响
PSC 越小分辨率越高，但最大周期越短（16 位溢出）
PSC=71（1MHz）分辨率 1µs，最大周期 65.5ms（约 15Hz 以上）
PSC=719（100kHz）分辨率 10µs，最大周期 655ms（约 1.5Hz 以上）

  1. PWM 输入模式为什么需要「从模式复位」？如果没有它，CCR1/CCR2 还能直接算周期和占空比吗？

    从模式复位让每个上升沿把 CNT 清零，于是 CCR1 直接就是「一个完整周期的计数」，CCR2 是「从上升沿到下降沿的计数」，两者同一基准，直接相除得占空比。没有复位时 CNT 自由跑，CCR 是绝对时间戳，要自己记录两次上升沿的差值并处理溢出，计算复杂且容易错。

  2. 1MHz 计数下，CCR1=2000、CCR2=500，信号的频率和占空比是多少？如果 PSC 改成 719，同样的波形 CCR1/CCR2 会变成多少？

    1MHz 时周期 2000µs=2ms → 500Hz；占空比 500/2000=25%。PSC=719 时计数 100kHz（10µs 一个数），周期 2ms 对应 200 个数，高电平 0.5ms 对应 50 个数，即 CCR1=200、CCR2=50，比值不变。

  3. 为什么 PWM 输入模式比「单通道双边沿捕获」更适合测占空比？

    单通道双边沿要在回调里切换极性（上升→下降→上升），每次切换都有软件延迟，且切换期间可能漏掉边沿；高占空比/高频时尤其明显。PWM 输入模式用两个硬件捕获通道同时工作，边沿由硬件分派，不需要软件干预，读数稳定且不占 CPU。

  4. 读航模接收机的 5V PWM 信号，直接接 PA6 有什么风险？怎么判断能不能直连？

    PA6 在 F103 上不是 FT（5V 容忍）引脚时，5V 输入会通过内部保护二极管灌电流，长期可能损坏芯片；即使是 FT 脚，也只能承受有限电流。查数据手册引脚表的 FT 标记：带 FT 的可 5V 输入，但仍建议串 1kΩ 限流；不带的必须分压（如 10k/20k）或用电平转换芯片。最稳的是先量信号高电平，再决定。

一、I2C 时序：两根线怎么说话
SCL ─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─
     └─┘ └─┘ └─┘ └─┘ └─┘
SDA ──┬───┬───┬───┬───┬───
      S   A6  A5 ...  P
  • 起始（S）：SCL 高时 SDA 由高变低；
  • 地址：7 位地址 + 1 位读写位（0 写、1 读）；
  • ACK：第 9 个时钟，从机把 SDA 拉低表示收到；
  • 数据：每 8 位 + 1 位 ACK，高位在前；
  • 停止（P）：SCL 高时 SDA 由低变高。

关键电气特性：

  • SDA/SCL 都是 开漏，必须外接上拉（常用 4.7kΩ；速率高/线长时 2.2kΩ）；
  • 多器件挂同一总线，靠地址区分；地址冲突（同型号多片）要用地址脚改地址或加 I2C 多路复用器；
  • 标准模式 100kHz、快速模式 400kHz；F1 的 I2C 支持到 400kHz。

  1. MPU6050 的 7 位地址是 0x68，为什么 HAL 里要传 0x68 << 1？读和写时这个值有什么不同？

    HAL 的地址参数是 8 位格式：高 7 位是器件地址，最低位是读写位。0x68 << 1 = 0xD0 是最低位为 0 的写地址；HAL 在接收函数里会自动把最低位置 1（0xD1）表示读。直接传 0x68 会被当成 8 位地址 0x68（7 位地址 0x34），从机不响应。

  2. I2C 的 SDA/SCL 为什么必须开漏并加上拉？如果误配成推挽，可能出现什么现象？

    I2C 是多器件「线与」总线，任何器件只能拉低、释放时高阻，高电平由上拉提供。推挽输出会主动驱动高电平，当另一个器件拉低时形成电源到地的低阻通路，电流过大可能损坏器件；同时「线与」逻辑被破坏，仲裁失败。典型现象是通信偶发失败、波形高电平被拉低、器件发热。

  3. 写一个 I2C 寄存器型器件（如 MPU6050 的 0x6B）用哪个函数？它内部的时序与 Master_Transmit 有什么不同？

    用 HAL_I2C_Mem_Write(&hi2c, addr, reg, I2C_MEMADD_SIZE_8BIT, buf, len, timeout)。它先发起始 + 地址（写），再发寄存器地址，然后发数据，最后停止；Master_Transmit 只发地址 + 一段数据，不会自动插入寄存器地址。Mem_Read 则是「写寄存器地址 → 重复起始 → 读数据」，靠重复起始避免中途释放总线。

  4. 总线被从机钳住（SDA 一直低）时，为什么重新初始化 I2C 外设没用？正确的恢复步骤是什么？

    因为从机停在传输中间，仍握着 SDA；重新初始化只复位了主机状态机，从机没收到时钟，不会释放。恢复：把 SCL 配成普通开漏输出，手动发最多 9 个时钟脉冲，让从机把剩余位发完并释放 SDA；然后发一个停止条件（SCL 高时 SDA 低→高）；最后重新初始化 I2C。若仍无效，只能给从机断电复位。

{
    uint8_t cmd = 0x05, sr;
    do {
        CS_LOW();
        HAL_SPI_Transmit(&hspi1, &cmd, 1, 100);
        HAL_SPI_Receive(&hspi1, &sr, 1, 100);
        CS_HIGH();
    } while (sr & 0x01);
}

static void W25Q_EraseSector(uint32_t addr)
{
    uint8_t buf[4] = {0x20, (addr >> 16) & 0xFF, (addr >> 8) & 0xFF, addr & 0xFF};
    W25Q_WriteEnable();
    CS_LOW();
    HAL_SPI_Transmit(&hspi1, buf, 4, 100);
    CS_HIGH();
    W25Q_WaitBusy();
}

static void W25Q_PageWrite(uint32_t addr, const uint8_t *data, uint16_t len)
{
    uint8_t head[4] = {0x02, (addr >> 16) & 0xFF, (addr >> 8) & 0xFF, addr & 0xFF};
    W25Q_WriteEnable();
    CS_LOW();
    HAL_SPI_Transmit(&hspi1, head, 4, 100);
    HAL_SPI_Transmit(&hspi1, (uint8_t *)data, len, 1000);
    CS_HIGH();

}

  1. 每次写/擦前必须发 0x06（写使能），否则被忽略；

  3. 页编程不能跨 256 字节页边界，跨页要分段写。

  1. SPI 模式 0 和模式 3 的差别是什么？为什么 W25Q64 两种都能用？

    模式 0：CPOL=0、CPHA=0，空闲低电平、第一个（上升）沿采样；模式 3：CPOL=1、CPHA=1，空闲高电平、第二个（上升）沿采样。两者的采样沿都在上升沿，数据在下降沿变化，只是空闲电平不同。W25Q64 的时序允许这两种，所以 CubeMX 默认模式 0 即可；模式 1/2 则采样沿不同，会读错。

  2. W25Q64 页编程为什么不能跨 256 字节页边界？如果要写 500 字节，应该怎么写？

    页编程指令只更新页内地址的低 8 位，写到页尾会回卷到页首覆盖开头，所以跨页会破坏数据。写 500 字节要按页拆分：第一段写到本页剩余空间，第二段从下一页地址继续，最多 256 字节一段；每段写前发写使能、写后等 BUSY。擦除仍按 4KB 扇区做。

  3. 读 W25Q64 时，HAL_SPI_Transmit(&cmd) 之后为什么要再 HAL_SPI_Receive(buf)，而不是直接 Receive？接收时主机发的是什么？

    SPI 是全双工、主机产生时钟：从机只有在 SCK 跳动时才输出数据。Transmit 负责把指令字节发出去并产生 8 个时钟；随后 Receive 继续产生时钟，同时把从机输出的数据读进来。Receive 期间 MOSI 上发的是 dummy（通常是 0xFF），对从机无意义。若直接用 Receive，指令没发出去，从机不知道要干什么。

  4. 一个 SPI 总线上挂 W25Q64 和一块 SPI LCD，片选分别接 PA4、PB0。软件上要注意什么？

    ① 任一时刻只能拉低一个 CS，操作前拉低目标、操作完立刻拉高，未选中的保持高；② 两个器件的 SPI 模式/时钟可能不同，切换前用 HAL_SPI_DeInit/Init 或分别初始化不同 SPI 外设；③ 共用 SCK/MOSI/MISO 时，未选中器件的 MISO 应高阻，否则会打架；④ 不要在中断和主循环里同时操作同一 SPI 总线，加互斥或统一在主循环调度。

  1. DMA 的 Normal 与 Circular 模式有什么区别？ADC 连续采样和串口发一包数据分别该用哪个？

    Normal：搬完设定数量就停止，需要重新启动；Circular：搬完自动回到起点继续，计数器重装。ADC 连续采样用 Circular（不断覆盖缓冲区，配半完成/完成中断处理）；串口发送一包固定数据用 Normal（发完即停，进回调发下一包）。串口不定长接收常用 Circular + IDLE。

  2. 为什么 ADC1 的 DMA 请求只能接到 DMA1_Channel1？如果接到 Channel2 会怎样？

    因为 F1 的 DMA 请求映射是硬件固定的：每个外设请求线只连到特定通道，ADC1 固定在 DMA1_Channel1。接到其他通道后，该通道收不到 ADC 的请求信号，DMA 不会启动，表现为「ADC 在转换但缓冲区不变」。选通道必须查参考手册的 DMA 请求映射表或让 CubeMX 自动分配。

  3. __HAL_DMA_GET_COUNTER() 返回什么？在 Circular 模式下它如何变化？怎么用它算「已处理到哪」？

    返回当前剩余待传输数量（CNDTR）。Circular 模式下每搬一个数减 1，减到 0 后自动重装为总长度并回卷。用「总长 − 剩余」得到自上次重装以来已搬的数量；因为会回卷，主循环要结合半完成/完成中断或维护自己的读指针，不能只靠一次读数判断绝对位置。

  4. 用 DMA 把 1KB 数据从内存发到串口，发送期间 CPU 能做什么？发送完成后怎么知道缓冲区可以复用了？

    DMA 独立占用总线搬运，CPU 可以继续执行其他任务（取指会与 DMA 争总线，略有减速，但不阻塞）。发送完成后 DMA 触发中断，HAL 调用 HAL_UART_TxCpltCallback()；只有在这个回调里才能安全复用/释放该缓冲区。若在回调前改写，DMA 可能发出新旧混合的数据。

  2. 为什么 ADC 时钟不能超过 14MHz？72MHz 下应该怎么分频？

  1. RTC 用 LSE 32.768kHz 与 LSI ~40kHz 有什么区别？为什么产品里优先选 LSE？

    LSE 是外部晶振，频率精确（±20ppm 左右），走时误差小；LSI 是内部 RC，频率随温度/电压漂移（几十 ppm 到几百 ppm），一天可能差几秒。RTC 预分频按 32768 设计，用 LSI 还要按实际频率校正。产品要长时间准确走时，必须用 LSE + 纽扣电池。

  2. 停止模式唤醒后为什么要重新调用 SystemClock_Config()？不调用会怎样？

    停止模式会关闭 HSI/HSE 和 PLL，唤醒后系统默认回到 HSI 8MHz（或按恢复设置）。如果代码仍按 72MHz 计算波特率/定时器，实际时钟只有 8MHz，串口波特率会差 9 倍，输出全是乱码；定时器周期也全错。HAL 不会自动恢复，必须在唤醒后重配时钟，并重新初始化依赖时钟的外设。

  3. 待机模式与停止模式的本质区别是什么？为什么待机唤醒后程序像「重启」？

    停止模式只停时钟、保留 SRAM 和寄存器内容，唤醒后从 WFI 下一条继续执行；待机模式切断内核与大部分电源域，SRAM/寄存器内容丢失，唤醒相当于一次复位，程序从启动文件重新跑。所以待机适合「长时间休眠、醒来重新初始化」的场景，停止适合「短暂休眠、保持状态」的场景。

  4. 做一块电池供电的温湿度记录仪，每 10 分钟采一次数据，应该怎么组合 RTC、停止模式与看门狗？

    用 RTC 闹钟每 10 分钟唤醒一次；主循环采集 → 存 Flash/OLED → 进停止模式；停止前关传感器电源、GPIO 设模拟、HAL_SuspendTick()；唤醒后恢复时钟与外设。看门狗用 IWDG（LSI 独立），但注意停止模式下 IWDG 仍在跑，喂狗周期要覆盖唤醒后的处理时间，或在休眠前喂一次并让超时大于 10 分钟（不现实）——更常见的做法是休眠期间不依赖 IWDG，醒来后用软件检查任务是否完成。

一、CAN：差分总线上的多主通信

物理层

  • CAN_H / CAN_L 差分信号，抗干扰强，适合汽车/工控；
  • 两端各接 120Ω 终端电阻，否则反射导致误码；
  • 速率与总线长度成反比：1Mbps 约 40m，125kbps 可到 500m；
  • 需要 CAN 收发器（TJA1050/SN65HVD230），F1 的 CAN_TX/RX 是 TTL，不能直接上总线。

帧格式（标准帧）

SOF | 11 位 ID | RTR | IDE | DLC | 0–8 字节数据 | CRC | ACK | EOF
  • ID 既标识内容也决定优先级（ID 越小优先级越高）；
  • DLC 是数据长度（0–8）；
  • 标准帧 11 位 ID，扩展帧 29 位。

CubeMX + HAL

  1. Connectivity → CAN：Master Mode；
  2. Parameter Settings：Prescaler、Time Segments 按波特率算（如 72MHz、500kbps：Prescaler=9，BS1=4，BS2=3，SJW=1）；
  3. 引脚：PA11=CAN_RX、PA12=CAN_TX（F1 默认）；
  4. NVIC 勾 CAN RX0 中断（接收）。
CAN_HandleTypeDef hcan;

二、RS485：半双工的长距离串口

RS485 是「差分版串口」：A/B 两线、半双工、可挂 32 个节点、最长 1200m。需要一个收发器（MAX485/SP3485），并控制 DE/RE 引脚：

发送：DE=1（驱动总线）→ UART 发完 → 等 TC → DE=0（释放）
接收：DE=0（高阻接收）
#define RS485_DE_HIGH()  HAL_GPIO_WritePin(DE_GPIO_Port, DE_Pin, GPIO_PIN_SET)
#define RS485_DE_LOW()   HAL_GPIO_WritePin(DE_GPIO_Port, DE_Pin, GPIO_PIN_RESET)

void RS485_Send(uint8_t *buf, uint16_t len)
{
    RS485_DE_HIGH();
    HAL_UART_Transmit(&huart2, buf, len, 100);   /* 阻塞发完 */
    while (__HAL_UART_GET_FLAG(&huart2, UART_FLAG_TC) == RESET) { }  /* 等最后一位 */
    RS485_DE_LOW();
}
  • 发送后必须等 TC（发送完成）再释放总线，否则最后几个字节被截断；
  • 接收端在空闲时保持 DE=0；
  • 总线两端加 120Ω 终端电阻，必要时加偏置电阻。
三、单总线：DS18B20 / DHT11

单总线用一根线（外加 GND/电源）完成双向通信，靠「主机拉低不同时长」表示 0/1，对时序要求到微秒级。

{
    OW_LOW();

    else   { DWT_Delay_us(60); OW_RELEASE(); DWT_Delay_us(10); }

本课练习 · 4 题自编 · 按课程考点

  1. CAN 总线为什么需要 120Ω 终端电阻？只在一边接会怎样？

    CAN 是差分总线，信号在电缆末端会反射；120Ω 终端电阻与电缆特性阻抗匹配，吸收反射能量。只在一边接，另一端仍有反射，表现为波形过冲/振铃，高速或长线时误码率升高、通信不稳定。标准做法是总线物理两端各接一个 120Ω。

  2. RS485 发送完为什么必须等 TC 标志再拉低 DE？只等 TXE 会怎样？

    TXE 表示数据寄存器空、可以写下一个字节，但移位寄存器里可能还有最后一位没发完；此时拉低 DE 会释放总线，最后 1–2 位被截断，接收端收到错误帧。TC 表示「最后一个停止位也发完了」，此时释放才安全。用中断/DMA 发送时，要在 TxCpltCallback 里释放 DE。

  3. DS18B20 读回 85℃ 说明什么？为什么单总线时序里要避免长中断？

    85℃ 是 DS18B20 上电默认值，说明「启动转换后没等够 750ms 就读」，或者根本没转换成功。单总线的 0/1 靠微秒级高低电平宽度区分，中断打断会让主机拉低/释放的时间错位，从机解析成别的位；所以读写期间要关中断或用极短的临界区，微秒延时用 DWT 而不是 HAL_Delay。

  4. 用 ESP8266 通过 AT 指令联网，硬件上最容易忽略的两点是什么？

    ① 供电：ESP8266 峰值电流可达 300mA，STM32 板上的 3.3V LDO 通常带不动，必须独立 3.3V/500mA 电源并共地；② 电平与串口：ESP8266 是 3.3V，可直接接 STM32 的 USART，但要用交叉接（TX→RX），并且 AT 固件默认波特率可能是 115200 或 74880，先确认。还要留出 EN/GPIO0 的上拉，否则不启动。

    }
    return NULL;

typedef void (*pFunction)(void);
pFunction jump;

/* 1. 检查 APP 区是否有有效栈顶 */
uint32_t sp = *(volatile uint32_t *)APP_ADDR;
if ((sp & 0xFFFE0000) != 0x20000000) return;

/* 2. 关中断、复位外设 */
__disable_irq();
HAL_RCC_DeInit();
HAL_DeInit();

/* 3. 设 MSP、设向量表、跳转 */
SCB->VTOR = APP_ADDR;
__set_MSP(sp);
jump = (pFunction)(*(volatile uint32_t *)(APP_ADDR + 4));
jump();

  • SCB->VTOR = 0x08004000（HAL 可在 SystemInit 后设）；

本课练习 · 4 题自编 · 按课程考点

  1. 为什么嵌入式产品通常不建议用 malloc/free？内存池如何避免碎片？

    malloc 会在堆上按需切分，反复申请不同大小后留下许多不连续的小空洞，总空闲够但最大连续块不够，最终分配失败（碎片）。内存池预先切好固定大小块，分配/释放只是改标志位，O(1) 且不会产生大小不一空洞；代价是块大小固定、可能浪费一些空间。实时系统还要求分配时间可预测，malloc 不满足。

  2. FATFS 写文件后，为什么必须 f_close() 或 f_sync()？只 f_write() 就拔卡会发生什么？

    f_write 只把数据写入缓冲区/簇，FAT 表与目录项可能还没更新；f_close/f_sync 才会把缓存刷到卡上并更新 FAT。直接拔卡会导致文件长度、簇链不完整，轻则文件内容截断，重则整个分区损坏。产品里还要考虑掉电：定期 sync，或用日志式文件系统。

  3. USB CDC 与 UART 串口有什么本质区别？为什么 CDC 的波特率设置其实不影响速度？

    UART 是真正的异步串行，波特率决定位速率；USB CDC 是 USB 设备类，主机把它枚举成虚拟 COM 口，数据走 USB 批量端点，实际速度由 USB 全速 12Mbps 与主机轮询决定。CDC 的「波特率」只是线路编码参数，传给主机做兼容显示，不影响 USB 传输速率。

  4. IAP 中 Bootloader 跳转到 APP 前，为什么要设 MSP、设 VTOR、关中断？少做一步会怎样？

    设 MSP：APP 有自己的栈顶，必须让内核用 APP 的栈；设 VTOR：APP 的中断向量表在 0x08004000，不设则中断仍跳 Bootloader 的表，可能进错误处理；关中断：跳转前停止 Bootloader 的中断，避免跳转瞬间有中断进来。少设 VTOR 的典型现象是「APP 主循环能跑，但一进中断就死」；不设 MSP 可能栈越界。
