## 一、两种狗，两种脾气

| 项目 | 独立看门狗 IWDG | 窗口看门狗 WWDG |
| --- | --- | --- |
| 时钟源 | LSI（约 40kHz，独立于主时钟） | PCLK1（36MHz）经 4096 分频 |
| 计数器 | 12 位递减（0xFFF → 0） | 7 位递减（0x7F → 0x3F） |
| 喂狗限制 | 只要在溢出前喂就行 | **必须在窗口内喂**，太早也复位 |
| 主时钟坏了 | 仍能工作（LSI 独立） | 失效（依赖 PCLK1） |
| 典型用途 | 防程序卡死（最常用） | 检测「程序跑得太快 / 时序异常」 |
| 一旦启动 | **不能关闭**，只能复位 | 可以关闭 |

一句话选择：**只想防卡死，用 IWDG；要检测「任务执行时间异常」，用 WWDG**。绝大多数项目只用 IWDG。

## 二、IWDG：算清溢出时间

公式：

**T = (4 × 2^prer) × (RLR + 1) / 40000**

其中 `prer` 是预分频档位（0–6，对应分频 4、8、16、32、64、128、256），`RLR` 是 12 位重装值（0–4095），40kHz 是 LSI 的标称频率。

| 预分频 | 分频值 | RLR | 溢出时间 | 说明 |
| --- | --- | --- | --- | --- |
| 4（prer=0） | 4 | 4095 | 约 410ms | 太短，容易误复位 |
| 16（prer=2） | 16 | 4095 | 约 1.6s | — |
| 64（prer=4） | 64 | 625 | 约 1.0s | 1 秒档最常用 |
| 64（prer=4） | 64 | 4095 | 约 6.55s | 慢任务 |
| 256（prer=6） | 256 | 4095 | 约 26.2s | 上限 |

```c
#include "stm32f10x.h"

/* prer: IWDG_Prescaler_4/8/16/32/64/128/256；rlr: 0~4095 */
void IWDG_Init(uint8_t prer, uint16_t rlr)
{
    IWDG_WriteAccessCmd(IWDG_WriteAccess_Enable);   // ① 解锁（写保护）
    IWDG_SetPrescaler(prer);                        // ② 预分频
    IWDG_SetReload(rlr);                            // ③ 重装值
    IWDG_ReloadCounter();                           // ④ 先喂一次，避免立刻溢出
    IWDG_Enable();                                  // ⑤ 启动（启动后不能关）
}

/* 喂狗：把计数器重新装成 RLR */
void IWDG_Feed(void)
{
    IWDG_ReloadCounter();
}
```

**注意 LSI 不准**：40kHz 只是标称值，实际可能在 30–60kHz 之间（温漂大）。所以溢出时间有 ±50% 的误差。设计时按「最坏情况」留余量：想让狗 1 秒咬人，就按 0.5 秒来算喂狗周期。

## 三、WWDG：喂早了也咬人

WWDG 的计数器是 7 位的，从 0x7F 递减。它有两个界限：

| 界限 | 含义 |
| --- | --- |
| 窗口值 W[6:0] | 计数器高于这个值时喂狗 → **复位**（喂太早） |
| 0x3F | 计数器低于这个值就复位（喂太晚） |

所以合法喂狗区间是 `0x3F < CNT ≤ W`。窗口值由 `WWDG_SetWindowValue()` 设定，越低窗口越窄。

```c
void WWDG_Init(uint8_t tr, uint8_t wr, uint32_t fprer)
{
    RCC_APB1PeriphClockCmd(RCC_APB1Periph_WWDG, ENABLE);

    WWDG_SetPrescaler(fprer);        // WWDG_Prescaler_1/2/4/8
    WWDG_SetWindowValue(wr);         // 窗口上限（一般 0x5F 左右）
    WWDG_Enable(tr);                 // tr: 初始计数值（0x40~0x7F）
}

void WWDG_Feed(void)
{
    WWDG_SetCounter(0x7F);           // 重新装满
}
```

WWDG 的真实价值不在「防卡死」，而在「检测执行时间异常」：如果一个周期性任务本应 10ms 完成，你可以在任务开始时喂狗、任务结束时检查，一旦某次跑了 100ms，狗已经咬过了——这比 IWDG 的「卡死才复位」更敏感。

## 四、喂狗位置：这一条决定狗有没有用

| 喂狗位置 | 效果 | 评价 |
| --- | --- | --- |
| 主循环开头 | 主循环任何一步卡住 → 复位 | **正确** |
| 定时器中断里 | 主循环死了，中断还在喂 → 永远不复位 | **错误，最常见** |
| 每个任务结束时 | 任务没跑完就不喂 | 好（多任务系统） |
| 只在初始化后喂一次 | 等于没开狗 | 无效 |

:::warn 在中断里喂狗 = 白开看门狗
定时器中断是硬件触发的，只要时钟在、中断没被关，它就会一直进。主循环里 `while(1)` 卡死、I2C 死等、指针跑飞——这些都不会阻止定时中断继续喂狗。
所以狗永远不咬，问题永远暴露不出来。**喂狗必须放在「主循环走完一圈」这个位置**，让「主循环还活着」成为喂狗的前提。
:::

正确的用法是这样：

```c
int main(void)
{
    IWDG_Init(IWDG_Prescaler_64, 625);   // 约 1 秒

    LED_Init();
    OLED_Init();
    Key_Init();

    while(1){
        /* 业务：读按键、刷显示、算数据 */
        Key_Process();
        OLED_Refresh();

        /* 一圈都走完了，才喂狗 */
        IWDG_Feed();
    }
}
```

如果某次 `OLED_Refresh()` 因为 I2C 总线被拉死而卡住，主循环回不来，1 秒后狗就复位——设备自己恢复。这就是看门狗的全部价值。

## 五、调试时别被狗咬

调试阶段程序停在断点上，看门狗照样计数，1 秒后芯片复位，调试器断开——这就是「被狗咬」。

| 做法 | 说明 |
| --- | --- |
| `DBGMCU_Config(DBGMCU_IWDG_STOP, ENABLE)` | 调试暂停时冻结 IWDG 计数（推荐） |
| 调试时先不调 `IWDG_Enable()` | 最简单，但容易忘记加回来 |
| 把溢出时间调长（如 10 秒） | 断点停留时间够用 |

```c
/* 放在 main 开头，仅调试期有效 */
DBGMCU_Config(DBGMCU_IWDG_STOP, ENABLE);
DBGMCU_Config(DBGMCU_WWDG_STOP, ENABLE);
```

## 六、坑：一直复位、狗不咬、启用后无法下载

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 程序每隔约 1 秒重启一次 | 主循环里有耗时超过溢出时间的操作（如 OLED 刷整屏、Flash 擦除） | 加长溢出时间，或在长任务中间插喂狗 |
| 卡死了也不复位 | 喂狗写在中断里 | 移到主循环 |
| 下载后连不上调试器 | 程序一上电就启动 IWDG，复位太快来不及连 | 按住复位键下载；或用 `Connect under Reset` |
| 溢出时间与计算差很多 | LSI 实际频率偏离 40kHz | 按 ±50% 留余量，别卡着边界设计 |
| 擦 Flash 时被复位 | 擦除一页需要几十毫秒，超过短溢出时间 | 擦除前先喂狗，或把溢出时间设到秒级 |

:::tip 溢出时间该设多长
经验值：**最长一轮主循环耗时的 2–3 倍**。主循环 100ms，狗设 300ms；主循环 10ms，狗设 30ms。
设太长（比如 30 秒），设备卡死后要等半分钟才恢复，用户体验很差；设太短，正常的长任务会被误杀。
:::

## 练习
Q| LSI 按 40kHz 算，预分频 64、重装值 625，看门狗的溢出时间是多少？
A| 分频后计数频率 = 40000 / 64 = 625Hz，即每 1.6ms 减一。计数 626 次（RLR+1）→ 626 × 1.6ms ≈ 1.0 秒。
A| 由于 LSI 实际可能在 30–60kHz，真实溢出时间在 0.67–1.33 秒之间。所以喂狗周期要按 0.5 秒左右设计，留足余量。
Q| 为什么「在定时器中断里喂狗」等于没开看门狗？
A| 定时器中断由硬件触发，只要时钟在跑、中断没被屏蔽，它就会一直进——不管主循环是不是已经卡死。
A| 于是主循环死在某个 `while` 里，中断仍在喂狗，狗永远不咬，故障就永远暴露不出来。喂狗必须放在「主循环走完一圈」的位置，让它成为「主循环还活着」的证据。
Q| 独立看门狗一旦启动就不能关闭，这句话有什么实际后果？
A| 启动之后，只要程序没有按期喂狗，芯片就一定会复位，`IWDG_Disable` 之类的函数并不存在。所以「调试时先关掉狗」这条路走不通，只能用 `DBGMCU_Config` 在调试暂停时冻结计数。
A| 另一个后果：如果代码里有超过溢出时间的阻塞操作（大块 Flash 擦除、长时间延时），必须在中间插喂狗，否则功能永远做不完就被复位。
Q| 什么情况下该用窗口看门狗而不是独立看门狗？举一个具体例子。
A| 当「程序跑得太快」也是异常时。比如一个控制循环要求每 10ms 执行一次，如果某次因为逻辑错误 1ms 就转完了，说明某段代码被跳过——IWDG 检测不到（它只看你有没有卡住），WWDG 能：喂太早直接复位。
A| 典型场景：电机闭环控制、安全联锁、通信协议的超时检测。普通业务代码用 IWDG 就够了，WWDG 属于「对时序有硬性要求」的场合。
