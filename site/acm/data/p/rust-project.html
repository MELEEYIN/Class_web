最后一章把前面学过的东西拼起来：一个多线程 HTTP 服务器。它足够小（百来行），但用到了所有权、trait、Result、线程池、Arc/Mutex 和迭代器。

一、整体结构

src/
├── main.rs        // 监听端口，把连接交给线程池
├── lib.rs         // 公开 ThreadPool 给集成测试用
└── bin/main.rs    // 也可以拆成 bin

ThreadPool::new(4) → 固定 4 个 worker 线程
每个 TcpListener::incoming() 得到的连接 = 一个 Job
Job 通过 mpsc::channel 发给空闲 worker

二、线程池核心

use std::sync::{mpsc, Arc, Mutex};
use std::thread;

type Job = Box<dyn FnOnce() + Send + 'static>;

pub struct ThreadPool {
    workers: Vec<Worker>,
    sender: mpsc::Sender<Job>,
}

impl ThreadPool {
    pub fn new(size: usize) -> ThreadPool {
        let (sender, receiver) = mpsc::channel();
        let receiver = Arc::new(Mutex::new(receiver));
        let workers = (0..size)
            .map(|id| Worker::new(id, Arc::clone(&receiver)))
            .collect();
        ThreadPool { workers, sender }
    }

    pub fn execute<F>(&self, f: F)
    where F: FnOnce() + Send + 'static {
        self.sender.send(Box::new(f)).unwrap();
    }
}

关键点：mpsc 的 Receiver 不能克隆，所以用 Arc<Mutex<Receiver>> 让多个 worker 轮流取任务——这正是 “Arc + Mutex 共享可变状态” 的教科书用法。

三、处理请求

fn handle_connection(mut stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);
    let request_line = buf_reader.lines().next().unwrap().unwrap();

    let (status, filename) = match &request_line[..] {
        "GET / HTTP/1.1" => ("HTTP/1.1 200 OK", "hello.html"),
        _ => ("HTTP/1.1 404 NOT FOUND", "404.html"),
    };
    let body = fs::read_to_string(filename).unwrap();
    let resp = format!("{status}\r\nContent-Length: {}\r\n\r\n{body}", body.len());
    stream.write_all(resp.as_bytes()).unwrap();
}

五、常见坑

  1. Job 忘了 Send + 'static：跨线程传递必须满足。
  2. worker 里 lock() 的作用域过大，导致所有 worker 串行。
  3. 用 unwrap 处理请求：一个畸形请求就能让线程 panic。
  4. 忘记 \r\n\r\n：HTTP 头与体之间必须有空行，否则浏览器一直转圈。
  5. 没有限制线程数：每个连接一个线程，高并发时直接耗尽资源。
