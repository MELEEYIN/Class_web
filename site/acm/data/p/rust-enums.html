Rust 的 enum 不是“一组整型常量”，而是一组可能形态：每个变体可以携带不同类型的数据。配合 match 的穷尽检查，它替代了 C 里的 tagged union + switch，而且不会忘写分支。

一、带数据的枚举

enum Shape {
    Circle(f64),                 // 半径
    Rect(f64, f64),              // 宽、高
    Triangle { base: f64, h: f64 },
    Empty,
}

fn area(s: &Shape) -> f64 {
    match s {
        Shape::Circle(r) => 3.14159 * r * r,
        Shape::Rect(w, h) => w * h,
        Shape::Triangle { base, h } => 0.5 * base * h,
        Shape::Empty => 0.0,
    }
}

四个变体带了三种不同的载荷（一个值、两个值、命名字段、没有值），C 里要写一个 struct + union + tag 才能做到，还得自己记得检查 tag。

二、match 的穷尽性

let n = 3;
let desc = match n {
    0 => "零",
    1 | 2 => "小",
    3..=9 => "中",
    _ => "大",          // 必须覆盖所有可能，否则编译失败
};
模式含义
0字面量
1 | 2或模式
3..=9区间（含右端）
x绑定变量，匹配一切
_忽略，不绑定

编译器会检查所有变体都覆盖到——这正是 Rust 里“加了一个枚举变体，代码编译不过”成为好事的原因：它逼你处理新情况，而不是运行时漏掉。

三、Option 与 Result 就是枚举

enum Option<T> { Some(T), None }

let v = vec![1, 2, 3];
match v.get(5) {
    Some(x) => println!("{}", x),
    None => println!("越界了"),
}

所以“可能为空”在 Rust 里不是靠 null，而是一个必须处理的值；? 运算符只是在 Result 上做了“失败就提前返回”的语法糖。

四、常见坑

  1. match 少写分支：报 non-exhaustive patterns，加 _ => ... 或补全。
  2. 把 Some(x) 写成 Some：漏了括号里的绑定。
  3. if let 只处理一种情况，剩下的静默忽略——需要分支时老实用 match。
  4. 匹配引用时类型不匹配：对 &Option<T> 要写 Some(x) => ...（自动解引用）或先 *。
  5. 以为 _ => () 是“什么都不做很安全”：它同样会吞掉本该处理的错误。

五、小结

枚举表达“几种可能”，match 保证“一种不漏”。到这里语法主干已通，下一批进入集合（Vec / String / HashMap）与错误处理。
