前面两件解决「值不值得写」和「写得快不快」，这一件解决最难的那个问题：你怎么知道自己是对的？只看代码是看不出来的 —— 你需要一台能自动挑错的机器。

3.1　为什么对拍是唯一可靠的调试手段「我觉得没错」不是证据

本质：写一个「肯定对但很慢」的暴力程序，再写一个随机数据生成器，让两者在同一份数据上跑 —— 输出不一致，就说明正解错了，而且数据自动给你留下来了。

为什么它比「盯着代码看」强这么多？因为三件事：

盯着代码看对拍
靠你对代码的理解 —— 而错误恰恰来自你理解错的地方，所以你看多少遍都看不出来靠两份独立实现的对比 —— 它们同时错在同一个地方的概率极低
只能覆盖你想到的情况。你没想到的边界，你也不会去测随机数据会跑出你没想到的组合，这才是它真正的价值
发现错了之后，还得自己造一组能复现的数据，可能花掉半小时停下时数据已经存在 in.txt 里了 —— 直接拿它去调

一句话把它的定位说清楚：对拍不能帮你想出解法，但能在你自以为想出来之后，用机器证明你错了。竞赛里「我觉得这题对了」和「这题确实对了」之间的距离，就是对拍填上的。

3.3　数据生成器：三个关键技巧决定对拍有没有用

对拍能不能抓到错，九成取决于生成器写得好不好。随机数乱撒只能撞到「普通的错」，而真正难查的是边界。

  1. 先小后大。从 n ≤ 8 开始。空数据、n=1、全负数、全部相等、严格递增这些边界错误，几乎一定在小数据里就暴露。而且小数据你还能手动推演，知道到底哪一步错了。
  2. 构造特殊数据，不要纯随机。纯随机的数据「太普通」了。要专门生成：全部相同、严格递增、严格递减、只有 0、只有负数、最大和最小紧挨着。把这些形状混进随机流里（例如 30% 概率走特殊分支）。
  3. 卡住数据范围的边界。题目说 a ≤ 10⁹，那随机数就必须覆盖到 10⁹ 和 −10⁹。只在 [0, 1000] 里取数，永远试不出溢出和精度问题。

注意 ③ 那种「只在小数据里才出现的错误」和 ④ 那种「只在最大数据里才出现的错误」是两类，都要覆盖。前者靠 mode 0～2，后者靠 mode 3。只有大数据的对拍会漏掉边界，只有小数据的对拍会漏掉溢出。

3.4　随机数：rand() 的四个坑本地能跑、评测机不对，多半是这里

同一个 rand()，在 Windows 和 Linux 上能生成的数值范围差了五个数量级。

坑后果怎么绕开
1. RAND_MAX 在 Windows 上只有 32767本地生成 n = 10⁵ 的数据时，所有值都挤在 0～32767 里，大数据才暴露的错误永远试不出来(rand() << 15) ^ rand() 手动拼；或直接换 <random> 的 mt19937
2. 不播种时序列完全一样每次跑都是同一组数据，对拍等于只测了一次srand(time(0) ^ (unsigned)clock())。注意要 XOR 上 clock()：time(0) 的粒度是秒，同一秒内启动两次种子相同
3. rand() % n 分布不均匀较小的数被生成得更多（除非 n 整除 RAND_MAX + 1）。数据「不够随机」，某些组合永远随机不到正式场合用 mt19937 + uniform_int_distribution
4. rand() * rand() 会溢出int 相乘直接爆掉，结果是负的或者很小先转 64 位：1LL * rand() * rand()，或者用上面的 << 15 ^ 写法

但也要说句公道话：在 OJ 上做题，rand() 加个 srand(time(0)) 通常就够了 —— 你是拿它造对拍数据，不是做密码学。换 mt19937 的理由只有一个：你写的生成器在 Windows 本地跑，数据规模上到 10⁵ 以上。

3.6　什么时候对拍不上不是所有题都能这么办

对拍能成立，靠的是「有暴力可写 + 答案可比较」这两根支柱。任意一根断了，就得换别的办法。

对拍失败时最危险的心态，是「对拍脚本报错了，说明是我脚本写错了」—— 然后去改脚本。先怀疑正解，再怀疑脚本。验证脚本本身对不对的办法：故意把正解改错一行（比如把 < 改成 <=），看对拍能不能抓出来。抓不出来，说明你的对拍是无效的。

3.7　对拍部分的七条常见错误每一条都会让你白跑一晚

1. 暴力程序本身就是错的

最致命的一条 —— 暴力和正解一起错，对拍永远显示「通过」，给你虚假的安全感。所以：先用题目给的样例验证暴力，或者用另一道更简单的同类题验证。暴力要写「笨到不用动脑」的版本，别在这里秀技巧。

2. 两边读入格式不一致

暴力读 n 之后读到行尾，正解读到行尾加一个空格 —— 这种差别会让两边吃到不同的数据，然后报一堆假错。暴力请直接复制正解的读入部分。

3. 生成器只生成小数据

小数据能抓边界，抓不到溢出和复杂度问题。让 n 在 1 到上限之间都取到，而且要有几档接近上限的。

4. 生成器只生成大数据

反过来同理。n = 10⁵ 的随机数据里出现「n = 1」或「全部相同」的概率是零，而这类边界恰恰是最容易写错的。

5. 用 rand() 生成 10⁵ 级的数据

Windows 上 RAND_MAX = 32767，生成不出真的大数 —— 而你在 Windows 上写、在 Linux 上测，就会看到「本地对拍通过、交上去 WA」。见 3.4。

6. 让暴力也开 O2、也做优化

暴力的价值就在于「简单到不可能错」。给它加优化、加剪枝，你就等于又写了一个可能错的正解。暴力就让它慢。

7. 对拍脚本没有退出条件

一直 while true 跑下去，忘了关就占着 CPU。设一个轮数上限或时间上限，跑够就自动停。

一个很实用的自检：把正解故意改错一个地方，跑对拍，看它几轮之内能不能抓到。如果跑了几千轮都没抓到，说明你的生成器覆盖得太差 —— 这比对拍本身更值得修。
