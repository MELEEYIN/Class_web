评测机给你的反馈只有那么几种。把它们和「固定的几个原因」对应起来，玄学错误就变成了查表。这一章的目标是：看到 RE 就知道先去看数组，看到 WA 就知道先去看边界。

4.1　本质：把玄学变成查表反馈少，但原因很固定

很多人卡住的原因是：评测机只告诉你一个词（WA），然后你就开始到处瞎改 —— 改一行、交一次、再改一行。这是在用提交次数代替思考。

正确的做法是把它当成有损的反馈信号：信号很粗，但每种信号背后可能的病因是有限且高度集中的。所以：

  1. 先分类：是哪一种错？（CE / RE / WA / TLE / MLE）—— 这一步就能砍掉 90% 的可能性。
  2. 再定位：每种错都有一个「最先查的清单」，按清单顺序查，别乱翻。
  3. 最后缩小：能自己复现的错才是好错。对拍就是用来把「WA」变成「一份具体的输入」的。

一个心态上的提醒：看到 WA 时不要问「我哪里写错了」—— 范围太大。要问「哪一个具体的输入会让它错」。前者是无解的开放问题，后者可以被对拍和边界分析一步步逼近。

4.2　六种结果 → 首要嫌疑按这张表顺序查

这张表建议打印出来。它不解决问题，但能让你不浪费时间在错误的方向上。

三种容易误判的情况：

  • RE 不一定是越界。在 Windows 上本地跑得好好的、交上去 RE，很可能是栈溢出（Linux 默认栈通常比 Windows 小）或者数组大小写死了。
  • WA 不一定是算法错。「输出格式」和「多组数据没清空」造成的 WA 比算法错更常见，而且更冤。
  • TLE 不一定是复杂度错。同一份代码、同一个 O(n log n)，有人 300ms 有人 2000ms —— 卡常是真实存在的（见第 2 章 2.4 / 2.5）。
4.3　WA 的五个最常见原因按出现频率排序
  1. 边界没特判。n = 1 时循环一次都不执行、n = 0 时数组长度为 0、序列全相等时某些假设不成立。写完代码先问一句「n 取最小是多少，这时会发生什么」。
  2. 爆 int。见下面 4.7 第一条。
  3. 多组数据没清空。上一组的残留跑到这一组里。写法：while (scanf("%d", &n) != EOF) { ...; memset(head, 0, sizeof head); }。注意全局数组才需要清，局部的一开始就是随机值更需要清。
  4. 输出格式。行末多了空格、少了换行、大小写不对、多输出/少输出一组、%.2f 的精度要求。这类错误"看起来完全对"，但对逐个字符比较的评测机就是错。
  5. 题意理解错。最常见也最贵：把「至少」看成「恰好」、漏掉一个约束、把 1-based 当成 0-based、忘了取模。做法：把题面的每一句话都翻译成一个具体条件，逐条对照代码。
4.4　RE 与 MLE：内存和越界大数组放哪儿，是这一节的全部重点

同一个 int[1000005]，写在 main 里是 4 MB 的「栈炸弹」，写在 main 外面却毫无压力。

为什么栈溢出特别难查？因为它不给你有用的信息：程序直接挂掉，没有「数组越界」的提示，甚至可能诡异地「跑完了但答案不对」。而且它在 Windows 本地可能完全正常（Windows 默认栈比 Linux 大）。所以不要靠试 —— 直接从写法上杜绝：大数组一律全局。

4.5　TLE 的排查顺序别一上来就怀疑算法

TLE 不是只有「复杂度算错了」一种原因。按这个顺序查，从最便宜的开始：

顺序查什么典型症状 / 修法
1死循环循环变量根本没变、while 条件永远成立、getchar 读到 EOF 后不退出（第 2 章 2.8 第 1 条）。先在本地跑小数据，看它是不是卡住了
2输入输出太慢cin 没关同步、满屏 endl、cout 逐个字符输出。修起来只有几行，收益最大
3没必要的重复计算循环里反复调 strlen / size()、反复 sort、把 O(1) 的东西算成 O(n)
4容器用法不对vector 忘了 reserve 导致反复扩容、map 该换 unordered_map、list 该换 vector
5递归太深 / 常数太大递归改迭代、把取模换成条件减法（第 1 章 P1045 那个优化）
6真的是复杂度不够到最后才怀疑这一步。这时候要重新做第 1 章那件事：估一遍复杂度，看和 n 的范围对不对得上
4.6　五个真正管用的调试手法按性价比排序
  1. 小数据手推。先自己造一组 n = 3 的数据，用笔算一遍正确答案，再让程序跑一遍。这一步能定位一半的问题，而且不需要写任何工具。
  2. 打印中间量。把关键变量在关键位置打到 stderr，看它在哪一步开始偏离预期。不要用小黄鸭，用 fprintf。
  3. 二分定位。把程序从中间截断，看前半段的结果对不对 —— 一次砍掉一半的代码嫌疑。
  4. assert。把「我认为一定成立的事」写成断言，让它自己报出来。提交前记得关掉（或开 O2，一般会自动关）。
  5. 对拍。前三招都用完了还是找不到，就上第 3 章那套。它不猜，它直接给你一份出错的数据。

为什么建议打到 stderr 而不是 stdout？因为调试输出混进 stdout 会让你自己都分不清哪一行是答案、哪一行是调试信息，严重时还会直接把正确的答案挤成 WA。stderr 不参与答案比较，安全得多。

4.7　三个最贵的坑 + memset 的真面目原文里的「最贵三坑」，展开讲

坑一：爆 int

两个 10⁹ 相乘 = 10¹⁸，早就超过 int 的上限（约 2.1×10⁹）了。关键是 int × int 不会自动变成 long long —— 它是先按 int 算完（已经溢出、结果未定义），再赋值给 long long。

✗ long long s = a * b; // a、b 是 int → 先在 int 里爆掉 ✓ long long s = 1LL * a * b; // 先转 64 位，运算全程在 long long 里

看到乘法、求和、阶乘、组合数，先把默认类型设成 long long。别等到 WA 了再回来查。

坑二：数组开小了 1

下标从 1 开始，却只开了 n 个 —— a[n] 就是越界。规则：从 1 开始 → 开 n + 5。多开 5 个不占多少内存，但能省你一次 RE。

坑三：多组数据忘清空

第二组数据读到上一组的残留，答案莫名其妙。养成习惯：每个「多组数据」的题，读完第一行就先写清空。另外注意：全局数组只在程序启动时清零一次，不是每组数据都清。

memset 的真面目：它按字节，不按元素

memset(ptr, 值, 字节数) → 把每个【字节】都设成这个值

这是理解 0x3f3f3f3f 的唯一钥匙（第 2 章 2.3 讲过）：

  • memset(dist, 0x3f, sizeof dist) → 每个字节 = 0x3f，一个 int 有 4 个字节，拼起来是 0x3f3f3f3f = 1061109567（不是 63）
  • 它只能用来设 0、-1、0x3f 这类「每个字节都相同」的值。想全设成 1 是做不到的 —— 那样得到 0x01010101 = 16843009
  • 要按元素赋值就用 fill：fill(dp, dp + n + 1, -1e18)，想设什么设什么
