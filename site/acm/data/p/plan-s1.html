1.1 竞赛程序长什么样

入门★★★打地基

本质：竞赛程序 = 几行 #include + 一个 main + 「从 cin 读进来，算完，从 cout 写出去」。结构比课本上见的任何程序都简单，唯一的门槛是每个标准名字都得先说明它在哪个头文件里。

一个最简的竞赛程序，骨架永远是这样。注意 #include 是按需写的——下面两行分别解决了 cin/cout 和 sort：

把它补成真正能上场的骨架，只多四样东西：常量、全局数组、多组数据循环、读写加速。

四个必须记住的点

  1. #include 是「按需」的，不是仪式。 用 cin/cout 就必须有 <iostream>；用 sort/max/lower_bound 就必须有 <algorithm>；用 vector 就必须有 <vector>。漏了的唯一表现是编译报 'sort' was not declared in this scope——报错停在调用处，病因却在文件开头。
  2. using namespace std; 只是让你写 cin 而不是 std::cin。代价是自建的名字可能和标准库撞车（你自己写了个 abs，就会和 std::abs 打架），竞赛场景下基本可以不管。
  3. endl 会强制刷新缓冲区，'\n' 不会。输出 10^6 行时 endl 触发 10^6 次系统调用，TLE 往往就是这么来的，而不是算法慢。
  4. return 0; 别省。 评测不看返回值，但少了它会有「main 没有返回」的警告，顺手写上只多 9 个字符。

一个程序是怎么变成 AC 的

提交之后，服务器上跑的也是同一条 g++，差别只在版本、优化级别和栈大小。所以「本地过样例」只说明语法没错，不说明算法对——见第 2.5 节对拍。

为什么这份资料一律不用「万能头」

网上绝大多数竞赛代码第一行都是 #include <bits/stdc++.h>，它一次引入 GCC 标准库的几乎所有头文件。本文全篇禁用，四个理由：

理由说明
它不是标准 C++bits/stdc++.h 是 libstdc++（GCC 自带）的私有实现，C++ 标准里根本没有这个头文件
换个编译器就不存在MSVC（Visual Studio、CLion 默认工具链）、Apple Clang 都没有它，本地写作业、课程实验里写它直接 CE
编译明显变慢它把三百多个头文件全部展开，一个空程序的编译从 0.2 秒变成 1 秒以上；模板越写越多，差距越大
看不出依赖别人（以及三个月后的你）无法从代码看出这个程序到底用了哪些库，改一行还得先猜

也要承认现实：洛谷、Codeforces、AtCoder 的 GCC 环境都支持它，机房里很多人也在用。会用不等于该依赖——真正省时间的是「一份固定 13 行的头文件模板」，而不是一个只在特定编译器上成立的技巧。第 1.2 节把这张表补齐，配好模板之后，你写 #include 的速度和写万能头没有区别。

💡 提示

本地编译建议：g++ a.cpp -o a -O2 -std=c++17 -Wall。-O2 开优化（评测机也开），-Wall 打开所有警告，-std=c++17 支持结构化绑定等新语法。

⚠️ 易错

「本地能编、交上去 CE」有九成是两件事：用了非标准扩展（<conio.h>、getch()），或者用了比评测机更新的标准（C++20 的写法）。本地永远显式写 -std=c++17，把环境和评测机对齐。

✅ 小结

先抄骨架，再谈算法。骨架里唯一需要动脑的地方是 #include 那几行——下一节就是为了让它变成肌肉记忆。

1.2 头文件对照表

入门★★★打地基

本质：C++ 没有「默认可用」的标准库名字。sort、vector、max、memset、sqrt 这些名字全都住在某个头文件里，#include 做的事就是把那个头文件的内容抄到你的代码最前面。所以漏头文件的报错永远长这样：'sort' was not declared in this scope——名字不存在，不是你不会用。

🎨 生活类比

头文件就是厨房的抽屉标签。你不知道打蛋器在哪个抽屉，就只能在厨房里瞎翻；报错 not declared 不是打蛋器坏了，是你还没打开那个抽屉。抽屉只有十几个，贴一次标签能用一辈子。

这一节把「什么名字住在哪个头」整理成可直接查的表。这张表比背算法有用：算法可以查书，漏一行 #include 就是 0 分。

1.3 变量、类型宽度与溢出

入门★★★打地基

本质：int 是 32 位，能装到 2.1×10^9 左右；long long 是 64 位，能装到 9.2×10^18。int 溢出不报错，直接回绕成负数——这是竞赛第一号爆零原因。

类型字节范围什么时候用
int4约 -2.1×10^9 ~ 2.1×10^9下标、计数器、答案不超过 10^9 时
long long8约 -9.2×10^18 ~ 9.2×10^18求和、乘法、答案可能超过 2×10^9
unsigned int / size_t4 / 8只含非负size() 返回值，不要和负数比较
short2约 ± 3.2×10^4省内存的二维数组（见 1.6）
char1通常是 -128 ~ 127字符、小整数
double815~16 位有效数字竞赛默认浮点类型
float46~7 位有效数字一般不用于计算

坑一：先溢出，再赋值

a * b 在 int 里算出来是 -1486618624 之类的垃圾，再赋给 long long 也救不回来。规则：只要两个可能超过 2×10^9 的数要相乘，就写 1LL *。 这是竞赛里最便宜的保险。

坑四：无符号数会把负数变成天文数字

坑五：long 是个陷阱

long 在 Windows（MinGW）上是 4 字节，在 Linux 上是 8 字节。同一份代码本地过、评测机溢出，是最难查的一类 bug。结论：永远不写 long，要么 int，要么 long long。

坑六：有符号溢出是「未定义行为」，不是「回绕」

-O2 下 GCC 会基于「有符号溢出不会发生」做优化，这段代码可能被优化成恒假。别用溢出后的值去判断溢出，直接用 long long。

坑七：char 有没有符号，标准没规定

竞赛里 char 只用来存 ASCII（0~127），超出这个范围就该换类型。

⚠️ 注意

一句话规则：看到「求和 / 乘积 / 答案上界不确定」就用 long long，看到「两个大数相乘」就加 1LL。

这四处都编译通过（-Wall 只能抓到一部分），交上去就是 WA 或 RE。结论：printf 的格式符和变量类型必须严格配对，long long 一律 %lld。

scanf 与 cin 混用：三条铁律

  1. 默认状态下可以混用，因为 cin 和 scanf 共享同一个缓冲区（sync_with_stdio 为真）。代价是两边都慢。
  2. 一旦关了同步，绝对不能混用。 关掉之后 cin 有自己的缓冲区，可能一次从文件里抢走 4KB，scanf 再去读就只能读到后面的数据——读入整体错位，而程序不报任何错。
  1. printf 与 cout 交替输出时，缓冲区各自独立，顺序会乱（cout 的还没 flush，printf 的先出去了）。要么全用一套，要么手动 cout.flush(); fflush(stdout);——但读入那半边仍然坏着。
⚠️ 易错

调试时用 cerr 打印中间变量是安全的：cerr 不缓冲、不参与 sync_with_stdio，任何时候都能立刻看到。这也是为什么第 1.15 节推荐 cerr 而不是 cout 做调试输出。

位运算外面一律加括号。 a & 1 == 1 恰好碰巧能跑（因为 1 == 1 是 true 即 1），但 x & y == 0 就彻底错了——这类 bug 编译器不会提醒你。

必背技巧

这些是 GCC 内建函数，不用任何头文件。C++20 的 std::popcount 在 <bit> 里，但多数评测机是 C++14/17，考场一律写 __builtin_ 版本。

子集枚举（状压 DP 的基础）

n ≤ 20 时 1 << n 是 10^6，可以枚举；n = 25 时是 3.3×10^7，勉强；n ≥ 31 时 1 << n 直接溢出，要 1LL << n（见 1.3）。

五个必须记住的坑

  1. 1 << 31 是 int 溢出，要写 1LL << 31。1 << 32 是 UB（移位位数 ≥ 类型宽度）。
  2. x >> k 对负数是算术右移，等于向下取整：-3 >> 1 == -2，而 -3 / 2 == -1。这两者不相等，涉及负数时不要互相替换。
  3. x % 2^k 和 x & (2^k - 1) 只在非负时相等：-5 % 4 == -1，但 -5 & 3 == 3。
  4. ~x 不是「相反数」，~x == -x - 1；想要相反数写 -x。
  5. __builtin_ctz(0) / __builtin_clz(0) 是 UB，返回什么都不保证。用之前先判 x != 0。

位运算的三大用途

  • 压状态：用一个整数的二进制位表示「哪些元素被选中」——这是状压 DP 的基础（第 5.7 节）。
  • 压常数：用 x >> 1 代替 x / 2（非负时结果相同，编译器其实也会自动做）。
  • 提供数学性质：异或的自反性（a ^ a = 0，a ^ 0 = a）能解决一大类「找落单」问题；前缀异或能解决「区间异或」。
✅ 小结

位运算只有三件事要记：加括号、1LL、负数别用移位代替除法。

1.13 浮点数与精度

入门★★★打地基

本质：double 是二进制浮点，只能精确表示「分母是 2 的幂」的分数。0.1 表示不了，所以 0.1 + 0.2 != 0.3。竞赛里浮点题的原则是：能用整数就不用浮点，非用不可就固定误差。

有效数字对比

类型字节十进制有效数字竞赛用途
float46~7基本不用（精度不够，还容易和 %f 混淆）
double815~16默认选择
long double12/1618~19精度要求极高的几何、大数运算

三条实用规则

  1. 几何题尽量不碰浮点。 点在线段哪一侧、线段是否相交、凸包转向——全部用叉积的整数符号判断，零误差。反例：用 double 算叉积判共线，坐标是 10^9 时乘积到 10^18，double 已经丢精度，共线判错。
  2. 实数二分固定跑 100 次，比写 while (r - l > eps) 安全（eps 选多小都不稳，选大了精度不够）。100 次迭代把区间缩到 2^-100，早就超过 double 的分辨率。
  3. 大数相减会丢精度。 1e18 - 1e18 + 1 这类运算在 double 下直接失效：1e18 的精度间隔已经是 128，加 1 完全没反应。

判 NaN

1.14 常用常量与模板骨架

为什么 INF 用 0x3f3f3f3f 而不是 INT_MAX？

最短路松弛时要算 dist[u] + w。如果用 INT_MAX（2147483647），加上任何正数就溢出成负数，dist[v] > dist[u] + w 这个判断立刻失效，直接得到错误答案。

0x3f3f3f3f 约 1.06×10^9，两个相加约 2.1×10^9，刚好还在 int 范围内。而且它有个额外好处：memset(a, 0x3f, sizeof a) 能一次性把整个 int 数组填成这个值（每个字节都是 0x3f），不用循环。

-Wextra更多警告（含符号比较）推荐
-std=c++17指定标准永远加，和评测机对齐
-g保留调试信息需要 gdb 时
-fsanitize=address,undefined抓越界、有符号溢出、空指针调试期必用
-D_GLIBCXX_DEBUGSTL 容器越界检查vector/set 的 [] 越界时用
-Wl,--stack,67108864把栈调到 64MB（MinGW）递归深度大时本地测试

-fsanitize 打开后，数组越界、有符号溢出、空指针会立刻报错并指出行号——这是新手最快的找 bug 工具，比单步调试快十倍。注意加了它之后程序会慢 2~5 倍，提交前一定要用不带它的版本编译。

💡 提示

Windows 上的 MinGW 常常不支持 -fsanitize=address，编译直接报错。替代方案：-D_GLIBCXX_DEBUG（抓 STL 越界）+ 手写 assert + -Wall -Wextra。WSL 或 Linux 环境下 ASan 完整可用。

五个调试手法

  1. 输出中间变量：在关键位置 cerr << "i=" << i << " ans=" << ans << '\n';（cerr 不缓冲，崩溃前也能看到输出）。
  2. 二分注释法：把后半段代码整段注释掉，看前半段是否正确——快速定位是哪一半出错。
  3. 小数据手推：自己造 n=3 的数据，在纸上一格一格走一遍，和程序的中间输出对照。
  4. 对拍：见第 2.5 节，这是最可靠的验证手段。
  5. 提交前删掉所有 cerr、assert 和调试输出——忘了删是经典爆零原因。

assert 的正确用法

评测机如果定义了 NDEBUG，assert 会被整个删掉（所以它不影响速度，但也不保护你）。本地调试期用它抓「不该发生」的情况，比等到输出错误再去倒推快得多。

计时：确认自己真的没超时

⚠️ 易错

本地跑 0.9 秒不代表能过——评测机可能慢一倍，而且 -O2 的优化效果和你本地不一定一致。经验值：本地超过时限 50% 就要优化。

入门★★★打地基

本质：评测结果只有几类：CE（编不过）、RE（跑崩）、WA（答案错）、TLE（太慢）、MLE（内存超）、PE（格式错）。每一类都有固定的排查顺序，先分类再定位，比盲目看代码快十倍。

第三类：WA（答案错误）→ 按顺序排查这六条

  1. 没开 long long：求和、乘积、答案超过 2×10^9（见 1.3）。
  2. 多测没清空：全局数组、vector、map 上一组的数据还在（见 1.14）。
  3. 边界没判：n=1、空串、全相同、全不同、0 或负数。
  4. 格式符错：%d 打了 long long，%.2f 忘了 fixed（见 1.4）。
  5. 取模出错：减法没补正、乘法没 1LL（见 1.14）。
  6. sort 比较函数不满足严格弱序：用了 <=（见 1.8）。

第四类：TLE（超时）→ 先算复杂度，再看常数

  • 先按第 2.2 节算：n=10^5 的 O(n^2) 是 10^10，必超。
  • 常数问题：endl（见 1.4）、没关同步、map 查 10^6 次（见 1.11）、vector 反复扩容没 reserve。
  • 递归函数返回值是大对象（每次复制一个 vector）。

第五类：MLE（内存超限）→ 看三个地方

  • 数组开太大（10^8 个 int = 400MB）。
  • set/map 节点开销（10^6 个约 50MB，见 1.11）。
  • 递归里开了局部数组，或者 vector 嵌套层数太多。

第六类：PE（格式错误）→ 只看两个地方

  • 行末多了一个空格（cout << a[i] << " " 在最后一个元素也加了空格）。
  • 少/多了空行。惯用写法：cout << a[i] << " \n"[i == n];——最后一个元素输出换行，其余输出空格。
⚠️ 易错

评测机只告诉你「WA on test 3」，不告诉你测试点内容。所以本地必须学会自己造数据、自己对拍（第 2.5 节）——这是唯一能在提交前发现问题的手段。
