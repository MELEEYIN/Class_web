1 · 复杂度分析：一分钟算出「能不能过」

复杂度分析不是数学，是一种手感。它要解决的唯一问题是：给我 n 的范围，我能不能在 1 秒内跑完？这个反应要快过想解法本身。

看这张图有两个要点：

  1. 纵轴是对数轴，视觉上的"陡"被压扁了。真实情况比图上可怕得多：n 从 10³ 涨到 10⁶（才 1000 倍），O(n²) 的运算量涨了 10⁶ 倍。
  2. 交点才是重点。O(n²) 大约在 n ≈ 10⁴ 处触线，O(n³) 在 n ≈ 460 处就爆了。这两个数要背下来 —— 拿到题先看 n 的范围，立刻能反推"这题允许我用什么复杂度的算法"。

工程上够用的换算：C++ 一秒大约 10⁸ 次简单运算（加减、比较、移位）。取模与除法慢 10～20 倍；递归调用和 STL 容器再打个折。所以实做时一般在 10⁷ ~ 10⁸ 这个区间卡安全线。

注意：复杂度是渐进行为，不是性能承诺。同一个 O(n log n)，手写归并和 std::sort 的常数差好几倍；同一个 O(n)，用 cin 读入和使用 scanf 也可能差一倍。

1.4　六种循环形状速查扫一眼形状就出结论

复杂度分析在实战里不是逐行推的，是扫一眼循环的"形"就出结论。这六种覆盖了 90% 的场景。

  • O(n)：i 每次 +1 走到 n，就是 n 次。前缀和、双指针都是这个形状。
  • O(n²)：两个独立变量各走 n 次，乘起来。Floyd 的三重循环里 k 在外层，本质还是 n×n 的两维状态表；冒泡排序比较次数是 n(n−1)/2 → 去掉系数还是 n²。
  • O(log n)：n 每次折半，问"能折多少次"。2^k ≤ n ⟹ k ≤ log₂n。它不跟 n 成正比，而跟 n 的位长成正比 —— n = 10⁶ 时 log₂n 只有 20。
  • O(n log n)，排序型：std::sort 是 O(n log n)，不是 O(n)。这是最常被白送的一条。
  • O(n log n)，嵌套型：外层线性、内层折半，两者相乘。KMP 里那个 while 的跳转是均摊 O(1) 的；树状数组每个操作 O(log n)。
  • O(n³)：三层嵌套。区间 DP、矩阵乘法、高斯消元。n = 500 就是它的天花板。

最容易吃亏的是第 4 种。有人在一个 O(n²) 的循环里顺手 sort 一遍，复杂度没变但常数翻了好几倍；更糟的是在 O(n log n) 的外层循环里 sort，直接退化成 O(n² log n)。

1.5　调和级数：最容易数错的形状步长是 i 而不是 1

这是这一节真正的技术核心。原文那个例子，放大来看：

看第二层，不要看 n，要看 j 怎么变。j 取的值是 i, 2i, 3i, … 直到超过 n，所以它的执行次数是 ⌊n / i⌋。于是总次数是各层相加：

总次数 = Σ(i=1..n) ⌊n / i⌋ = n · (1 + 1/2 + 1/3 + … + 1/n) = n · H(n)

H(n) 是调和数，H(n) = ln n + γ + O(1/n)，其中 γ ≈ 0.5772 是欧拉常数。所以：

n · H(n) ≈ n · ln n ≈ 0.693 · n · log₂ n ⟹ O(n log n)

以 n = 16 为例：每根柱子的高度就是内层的执行次数 n/i，柱顶落在双曲线 n/i 上。左边第一根一根就抵得上右边一堆 —— 面积按 n·ln n 增长，不是 n²。

为什么换底不影响复杂度：log_a n = log_b n / log_b a，只差一个常数因子，而 O() 里所有常数都丢掉。所以写复杂度时不必纠结 log 的底。

1.6　三层循环：系数丢掉，量级不变内层平均只走一半，仍然是 O(n³)

一层层数。内层 k 从 j 走到 n，次数是 n − j + 1。对 j 求和：

Σ(j=1..n) (n − j + 1) = n + (n−1) + … + 1 = n(n+1)/2

再乘上外层 i 的 n 次：

n · n(n+1)/2 = n²(n+1)/2 ⟹ O(n³)

系数是 1/2，但复杂度不写系数。这是这里唯一的考点：1/2·n³、100n³、n³ + 5n² 全都写成 O(n³) —— 因为大 O 只关心增长的量级，不关心常数。

由此得一条省事的判断法则：三层 for、每层变量都是 ±1 变化、边界都跟 n 同阶 → 答案基本就是 O(n³)。只有当某个循环变量的变化方式不是 ±1（j += i、k /= 2，或起点依赖外层且步长随外层变），量级才可能变成 n³ 以外的东西。

1.7　例题：洛谷 P1045 麦森数同一道题，两个子问题差 10⁶ 倍

这题的价值不在算法，在于它把"同一道题里，两个子问题的复杂度可以差好几个数量级"演示得极清楚。

题目：求 2ᵖ − 1 的位数与最后 500 位，p ≤ 3.1 × 10⁶（输出末 500 位，每行 50 位，共 10 行）。

第一问：位数 —— O(1)，一行公式

记 d(x) 为 x 的十进制位数，则 d(x) = ⌊log₁₀ x⌋ + 1。代入 x = 2ᵖ：

d(2ᵖ) = ⌊log₁₀ 2ᵖ⌋ + 1 = ⌊p · log₁₀ 2⌋ + 1

为什么 2ᵖ − 1 的位数和 2ᵖ 一样？因为 2 的幂的末位只可能是 2、4、8、6，永远不是 0，所以 2ᵖ 不是 10 的倍数，减一绝不会跨越 10ᵏ 这条边界。

p = 3.1×10⁶ 时：3.1×10⁶ × 0.3010299957 ≈ 933192.99 → 933193 位。

浮点精度够不够？够。double 有约 15.95 位十进制有效数字，而这里 p·log₁₀2 只有 6 位整数部分，绝对误差在 10⁻¹⁰ 量级，远小于 1，判定 ⌊·⌋ 绝对可靠。这题不需要高精度求位数 —— 很多人上来就写高精度，属于没估复杂度。

第二问：末 500 位 —— 必须高精度

思路是把"两位十进制"折成"八位十进制"来压块，同时利用"只乘 2"这个特殊结构把除法全部消掉 —— 因为底数固定是 2，进位只可能是 0 或 1，所以可以把最慢的 % 和 / 换成一次比较和一次减法。

复杂度：内层迭代 p × LEN ≈ 3.1×10⁶ × 65 ≈ 2×10⁸ 次。乘法和比较都很便宜，落在 1 秒的安全线内。

进阶写法：用快速幂把指数压到 log p。关键在于一个洞察 —— "只保留低 500 位"在乘法下是封闭的：进位只向高位走，高位不会反过来影响低位，所以每次乘完直接截断是合法的。这样只需要约 2·log₂p ≈ 44 次 500 位 × 500 位的乘法，每次约 65² = 4225 次块乘，总量约 2×10⁵ —— 比上面快三个数量级。

1.8　七条常见错误比上面所有内容都值钱

1. 把 O(log n) 写成 O(√n)

判别标准只有一个：看变量的变化方式。

试除法求单个数的质因数分解是 O(√x)，不是 log。记忆口诀：折半才是 log，逐个试永远是线性 —— 哪怕上界只有 √n。

  • unordered_map：平均 O(1)，但最坏 O(n) —— 会被出题人专门构造数据卡掉

5. 递归要看递归树，不是看代码行数

朴素斐波那契 f(n) = f(n−1) + f(n−2) 是 O(2ⁿ)；加一个记忆化数组后是 O(n)。同一个式子，两种复杂度，差别就是"有没有把重复子问题存下来"。

6. 只算时间不算空间

见 1.3 数据规模对照表 里的提醒：int[10⁸] 是 400 MB，bitset<10⁸> 只要 12.5 MB。

7. n 很小时，常数因子会反过来咬你

n = 100 时，一个循环体极简的 O(n²) 可能跑得比常数很大的 O(n log n) 快。复杂度是渐进行为，不是性能承诺 —— 这也是为什么"能不能过"要按实际 10⁸ 的基准去算，而不是只看阶。

2 · 竞赛代码脚手架：快读、快写与常用宏

把「每次都写一遍」的东西固化成模板，比赛时在编辑器里 Tab 一下出来。省下的不是几秒钟，而是打断思路的次数。但脚手架也是最容易埋坑的地方 —— 一层一层看，每层都要知道自己在拿什么换什么。

2.1　脚手架的四个层次每层的取舍不一样

脚手架不是「一堆宏」，而是四层职责完全不同的东西。分清楚层次，才知道哪些能省、哪些不能省。

越靠上的层，影响面越大：头文件决定「能不能编译」，宏只决定「代码短不短」。

一个反直觉的结论：四层里最不值得省的是第一层（头文件）。多写几个 #include 只花你两秒钟，写错一个头文件或者用了非标准的万能头，代价是换环境就编译不过。而最值得花时间打磨的是第三层（输入输出）—— 它直接决定会不会 TLE，而且改起来只有几行。

第四层（宏）要刻意克制：宏没有类型检查、没有作用域、报错信息指向宏定义而不是你的调用点。它能把代码写短，也能让你花半小时找一个本来 30 秒就能看出来的错误。

2.2　第一层：头文件 —— 为什么不该用万能头含 23 行对照表 + 一个中肯的例外

很多模板第一行是 #include <bits/stdc++.h>，看起来「一行顶所有」。它确实能在 GCC 上跑通 —— 问题在于代价。

问题说明
不是 C++ 标准的一部分它是 GCC 私有的实现细节（依赖 libstdc++）。换到 MSVC、部分 clang 的严格模式、某些评测机或真实工程里，直接编译不过。
编译明显变慢它把上百个标准头一次性展开。编译一个空程序：用万能头要 1 秒以上，只引 <cstdio> 不到 0.1 秒。小型 OI 题你感觉不到，但它会纵容你永远不看自己用了什么。
学不到「谁在哪个头文件里」面试、笔试、看别人代码、改真实工程时，这个知识是硬需求。早期养成按需 include 的习惯，成本最低。

一个中肯的例外（原文没说，但你应该知道）：在洛谷、Codeforces 这类 GCC 评测机上，万能头确实能用，而且省下的两秒钟在 3 小时比赛里也不是完全无所谓。所以这不是「道德问题」，而是一个成本判断：

  • 长期收益明确：按需 include 让你知道自己用了什么，这个能力会一直复利。
  • 短期代价极低：多写 3 行 #include。
  • 所以结论是「当习惯用按需」，而不是「用了万能头就是错的」。赶时间的正式比赛里用了也不必自责 —— 只要你知道代价是什么。
  • 但有两种场合绝对不要用：投简历的代码、任何给别人看/交付的工程代码。

2.3　第二层：别名与常量 —— INF 为什么偏偏是 0x3f3f3f3f原文提到但没解释，这里补上
INT_MAX = 2147483647 = 0x7FFFFFFF 0x3f3f3f3f = 1061109567 （≈ 1.06 × 10⁹）

两个都是「很大的数」，为什么求最短路、做 DP 时几乎所有人用后者？三个原因，每一个都实在：

① 加自己不会溢出

松弛操作里最常见的一句是 dist[v] = min(dist[v], dist[u] + w)。如果 dist 的初值是 INT_MAX，那么当 dist[u] 还是无穷大时，dist[u] + w 就溢出了 —— 有符号整数溢出是未定义行为，结果是负数，于是「无穷大 + 边权」变成了一个很小的数，被当成更优解取走，答案彻底错掉。

INT_MAX + INT_MAX = 4294967294 > 2147483647 ✗ 溢出 0x3f3f3f3f × 2 = 2122219134 < 2147483647 ✓ 安全

用 0x3f3f3f3f 时，两个「无穷大」相加仍然小于 INT_MAX，所以松弛时不会翻车。

② 可以用 memset 一键初始化

memset 是按字节填充的，只能填「四个字节都相同」的值。

memset(a, 0x3f, sizeof a) → 每个字节 0x3f → int = 0x3f3f3f3f ✓ memset(a, 0x7f, sizeof a) → 得到 0x7f7f7f7f，并不是 INT_MAX ✗

所以 INT_MAX 根本没法用 memset 批量赋值，只能老老实实写 for 循环 —— 在 n = 10⁶ 的图上这就是一次白送的常数开销。

③ 余量刚好够用，不多不少

0x3f3f3f3f ≈ 1.06×10⁹ 比大多数题目的最短路上界（10⁹ 量级）大一点点，又比 INT_MAX 小一半，给「累加两三次」留出了空间。long long 版本对应的是 0x3f3f3f3f3f3f3f3fLL。

顺手一个同类坑：取模常量写成 const int MOD = 1e9 + 7; 是错的说法 —— 1e9 是 double 字面量，赋给 int 会发生隐式转换。直接写 1000000007，或者写成 const ll MOD = 1e9 + 7;。需要整型常量的场合（constexpr、模板参数、位运算）会因此出意外。

2.6　第四层：常用宏 —— 该用的、要小心的、不要用的这一节最能拉开差距

宏在 C++ 里是「文本替换」，它没有类型检查、没有作用域、报错时指向宏定义而不是你的调用点。所以判断标准很简单：这个宏会不会在你没防备的时候悄悄改变语义？

分档依据只有一条：调用点有没有可能出现「你没想到的展开结果」。

为什么 #define int long long 是毒宏

它看起来能「一键防溢出」，一次解决所有爆 int 的烦恼。代价是三个：

  1. 所有 int 型数组内存直接翻倍。int a[10⁷] 从 40 MB 变成 80 MB，原本能过的题变成 MLE。
  2. printf("%d", x) 输出错乱。x 实际是 64 位，而 %d 按 32 位解释 —— 这是未定义行为，结果莫名其妙（要改成 %lld，可你满屏都是 %d）。
  3. int main() 会变成 long long main()，编译不过。于是你被迫写 signed main() —— 用另一个非标准的写法去补前一个的洞。一个坑引出两个坑，这就是它最坏的地方。

同样危险的「函数式宏」

三条能省下大量调试时间的规则：

  1. 宏只用来写「控制流简写」（rep / per / all），不用来写「求值」。凡是参数会被计算的东西，一律用 inline 函数或模板。
  2. 所有宏名加长度：mx → mxv、mn → mnv、l → lft、r → rgt。宏是全局文本替换，撞车时报错信息完全指不到问题所在。
  3. 宏体里每个参数都加括号、整体再加一层括号，否则 sqr(a + b) 会变成 a + b * a + b。

2.8　脚手架部分的九条常见错误每一条都真的会让人卡住

1. 快读里没判 EOF → 死循环

EOF = −1，而 −1 < '0' 恒真，所以跳过非数字的第一个 while 永远成立。必须在里面加 if (c == EOF) return 0;。

2. 用 char 接 getchar() 的返回值

getchar() 返回 int，因为要在 0~255 之外再表示一个 EOF。用 char 接的话，EOF 和字符 0xFF 混在一起，EOF 判断直接失效，接着就是死循环或乱码。

3. 混用 printf 和 cin

写了 sync_with_stdio(false) 之后两者各用各的缓冲，输出顺序会乱。选一套用到底。

4. sync_with_stdio(false) 写在读入之后

它必须在任何 IO 发生之前调用。写在 main 中间或某个函数里等于没写。

5. 用 endl 当换行

每次强制 flush。输出 10⁶ 行能慢好几倍，是 TLE 高频原因。

6. 缓冲快写忘了收尾 flush

最后不到 1 MB 的输出全部丢失，表现是「本地对、交上去只错最后几行」。

7. const int MOD = 1e9 + 7;

1e9 是 double 字面量。写 1000000007。

8. 大数组开在 main 里（局部变量）

局部变量在栈上，Windows 默认栈只有 1~8 MB。int a[1000005] 是 4 MB，看起来没事，但多开几个就 RE（而且是「莫名奇妙的 RE」，因为栈溢出不会给你友好的提示）。一律写成全局变量，或加 static。

9. 忘记 assert 要关掉

assert 在本地帮你自检很爽，但正式提交时如果没定义 NDEBUG，它会被执行 —— 大循环里的 assert 可能直接把程序拖成 TLE。开 O2 通常会自动关掉，但别赌。

还有一个跨平台的坑（对拍时最常撞）：RAND_MAX 在 Windows 上只有 32767，Linux 上是 2³¹−1。所以 rand() 在 Windows 本地根本出不了大数 —— 想生成 10⁶ 级的随机数得手动拼：rand() * rand() 或 (rand() << 15) ^ rand()，或者直接用 <random> 的 mt19937。

3 · 对拍：用随机数据证明自己是对的

前面两件解决「值不值得写」和「写得快不快」，这一件解决最难的那个问题：你怎么知道自己是对的？只看代码是看不出来的 —— 你需要一台能自动挑错的机器。

3.1　为什么对拍是唯一可靠的调试手段「我觉得没错」不是证据

本质：写一个「肯定对但很慢」的暴力程序，再写一个随机数据生成器，让两者在同一份数据上跑 —— 输出不一致，就说明正解错了，而且数据自动给你留下来了。

为什么它比「盯着代码看」强这么多？因为三件事：

盯着代码看对拍
靠你对代码的理解 —— 而错误恰恰来自你理解错的地方，所以你看多少遍都看不出来靠两份独立实现的对比 —— 它们同时错在同一个地方的概率极低
只能覆盖你想到的情况。你没想到的边界，你也不会去测随机数据会跑出你没想到的组合，这才是它真正的价值
发现错了之后，还得自己造一组能复现的数据，可能花掉半小时停下时数据已经存在 in.txt 里了 —— 直接拿它去调

一句话把它的定位说清楚：对拍不能帮你想出解法，但能在你自以为想出来之后，用机器证明你错了。竞赛里「我觉得这题对了」和「这题确实对了」之间的距离，就是对拍填上的。

3.3　数据生成器：三个关键技巧决定对拍有没有用

对拍能不能抓到错，九成取决于生成器写得好不好。随机数乱撒只能撞到「普通的错」，而真正难查的是边界。

  1. 先小后大。从 n ≤ 8 开始。空数据、n=1、全负数、全部相等、严格递增这些边界错误，几乎一定在小数据里就暴露。而且小数据你还能手动推演，知道到底哪一步错了。
  2. 构造特殊数据，不要纯随机。纯随机的数据「太普通」了。要专门生成：全部相同、严格递增、严格递减、只有 0、只有负数、最大和最小紧挨着。把这些形状混进随机流里（例如 30% 概率走特殊分支）。
  3. 卡住数据范围的边界。题目说 a ≤ 10⁹，那随机数就必须覆盖到 10⁹ 和 −10⁹。只在 [0, 1000] 里取数，永远试不出溢出和精度问题。

注意 ③ 那种「只在小数据里才出现的错误」和 ④ 那种「只在最大数据里才出现的错误」是两类，都要覆盖。前者靠 mode 0～2，后者靠 mode 3。只有大数据的对拍会漏掉边界，只有小数据的对拍会漏掉溢出。

3.4　随机数：rand() 的四个坑本地能跑、评测机不对，多半是这里

同一个 rand()，在 Windows 和 Linux 上能生成的数值范围差了五个数量级。

坑后果怎么绕开
1. RAND_MAX 在 Windows 上只有 32767本地生成 n = 10⁵ 的数据时，所有值都挤在 0～32767 里，大数据才暴露的错误永远试不出来(rand() << 15) ^ rand() 手动拼；或直接换 <random> 的 mt19937
2. 不播种时序列完全一样每次跑都是同一组数据，对拍等于只测了一次srand(time(0) ^ (unsigned)clock())。注意要 XOR 上 clock()：time(0) 的粒度是秒，同一秒内启动两次种子相同
3. rand() % n 分布不均匀较小的数被生成得更多（除非 n 整除 RAND_MAX + 1）。数据「不够随机」，某些组合永远随机不到正式场合用 mt19937 + uniform_int_distribution
4. rand() * rand() 会溢出int 相乘直接爆掉，结果是负的或者很小先转 64 位：1LL * rand() * rand()，或者用上面的 << 15 ^ 写法

但也要说句公道话：在 OJ 上做题，rand() 加个 srand(time(0)) 通常就够了 —— 你是拿它造对拍数据，不是做密码学。换 mt19937 的理由只有一个：你写的生成器在 Windows 本地跑，数据规模上到 10⁵ 以上。

3.6　什么时候对拍不上不是所有题都能这么办

对拍能成立，靠的是「有暴力可写 + 答案可比较」这两根支柱。任意一根断了，就得换别的办法。

对拍失败时最危险的心态，是「对拍脚本报错了，说明是我脚本写错了」—— 然后去改脚本。先怀疑正解，再怀疑脚本。验证脚本本身对不对的办法：故意把正解改错一行（比如把 < 改成 <=），看对拍能不能抓出来。抓不出来，说明你的对拍是无效的。

3.7　对拍部分的七条常见错误每一条都会让你白跑一晚

1. 暴力程序本身就是错的

最致命的一条 —— 暴力和正解一起错，对拍永远显示「通过」，给你虚假的安全感。所以：先用题目给的样例验证暴力，或者用另一道更简单的同类题验证。暴力要写「笨到不用动脑」的版本，别在这里秀技巧。

2. 两边读入格式不一致

暴力读 n 之后读到行尾，正解读到行尾加一个空格 —— 这种差别会让两边吃到不同的数据，然后报一堆假错。暴力请直接复制正解的读入部分。

3. 生成器只生成小数据

小数据能抓边界，抓不到溢出和复杂度问题。让 n 在 1 到上限之间都取到，而且要有几档接近上限的。

4. 生成器只生成大数据

反过来同理。n = 10⁵ 的随机数据里出现「n = 1」或「全部相同」的概率是零，而这类边界恰恰是最容易写错的。

5. 用 rand() 生成 10⁵ 级的数据

Windows 上 RAND_MAX = 32767，生成不出真的大数 —— 而你在 Windows 上写、在 Linux 上测，就会看到「本地对拍通过、交上去 WA」。见 3.4。

6. 让暴力也开 O2、也做优化

暴力的价值就在于「简单到不可能错」。给它加优化、加剪枝，你就等于又写了一个可能错的正解。暴力就让它慢。

7. 对拍脚本没有退出条件

一直 while true 跑下去，忘了关就占着 CPU。设一个轮数上限或时间上限，跑够就自动停。

一个很实用的自检：把正解故意改错一个地方，跑对拍，看它几轮之内能不能抓到。如果跑了几千轮都没抓到，说明你的生成器覆盖得太差 —— 这比对拍本身更值得修。

4 · 常见错误字典：看到结果就知道错在哪

评测机给你的反馈只有那么几种。把它们和「固定的几个原因」对应起来，玄学错误就变成了查表。这一章的目标是：看到 RE 就知道先去看数组，看到 WA 就知道先去看边界。

4.1　本质：把玄学变成查表反馈少，但原因很固定

很多人卡住的原因是：评测机只告诉你一个词（WA），然后你就开始到处瞎改 —— 改一行、交一次、再改一行。这是在用提交次数代替思考。

正确的做法是把它当成有损的反馈信号：信号很粗，但每种信号背后可能的病因是有限且高度集中的。所以：

  1. 先分类：是哪一种错？（CE / RE / WA / TLE / MLE）—— 这一步就能砍掉 90% 的可能性。
  2. 再定位：每种错都有一个「最先查的清单」，按清单顺序查，别乱翻。
  3. 最后缩小：能自己复现的错才是好错。对拍就是用来把「WA」变成「一份具体的输入」的。

一个心态上的提醒：看到 WA 时不要问「我哪里写错了」—— 范围太大。要问「哪一个具体的输入会让它错」。前者是无解的开放问题，后者可以被对拍和边界分析一步步逼近。

4.2　六种结果 → 首要嫌疑按这张表顺序查

这张表建议打印出来。它不解决问题，但能让你不浪费时间在错误的方向上。

三种容易误判的情况：

  • RE 不一定是越界。在 Windows 上本地跑得好好的、交上去 RE，很可能是栈溢出（Linux 默认栈通常比 Windows 小）或者数组大小写死了。
  • WA 不一定是算法错。「输出格式」和「多组数据没清空」造成的 WA 比算法错更常见，而且更冤。
  • TLE 不一定是复杂度错。同一份代码、同一个 O(n log n)，有人 300ms 有人 2000ms —— 卡常是真实存在的（见第 2 章 2.4 / 2.5）。
4.3　WA 的五个最常见原因按出现频率排序
  1. 边界没特判。n = 1 时循环一次都不执行、n = 0 时数组长度为 0、序列全相等时某些假设不成立。写完代码先问一句「n 取最小是多少，这时会发生什么」。
  2. 爆 int。见下面 4.7 第一条。
  3. 多组数据没清空。上一组的残留跑到这一组里。写法：while (scanf("%d", &n) != EOF) { ...; memset(head, 0, sizeof head); }。注意全局数组才需要清，局部的一开始就是随机值更需要清。
  4. 输出格式。行末多了空格、少了换行、大小写不对、多输出/少输出一组、%.2f 的精度要求。这类错误"看起来完全对"，但对逐个字符比较的评测机就是错。
  5. 题意理解错。最常见也最贵：把「至少」看成「恰好」、漏掉一个约束、把 1-based 当成 0-based、忘了取模。做法：把题面的每一句话都翻译成一个具体条件，逐条对照代码。
4.4　RE 与 MLE：内存和越界大数组放哪儿，是这一节的全部重点

同一个 int[1000005]，写在 main 里是 4 MB 的「栈炸弹」，写在 main 外面却毫无压力。

为什么栈溢出特别难查？因为它不给你有用的信息：程序直接挂掉，没有「数组越界」的提示，甚至可能诡异地「跑完了但答案不对」。而且它在 Windows 本地可能完全正常（Windows 默认栈比 Linux 大）。所以不要靠试 —— 直接从写法上杜绝：大数组一律全局。

4.5　TLE 的排查顺序别一上来就怀疑算法

TLE 不是只有「复杂度算错了」一种原因。按这个顺序查，从最便宜的开始：

顺序查什么典型症状 / 修法
1死循环循环变量根本没变、while 条件永远成立、getchar 读到 EOF 后不退出（第 2 章 2.8 第 1 条）。先在本地跑小数据，看它是不是卡住了
2输入输出太慢cin 没关同步、满屏 endl、cout 逐个字符输出。修起来只有几行，收益最大
3没必要的重复计算循环里反复调 strlen / size()、反复 sort、把 O(1) 的东西算成 O(n)
4容器用法不对vector 忘了 reserve 导致反复扩容、map 该换 unordered_map、list 该换 vector
5递归太深 / 常数太大递归改迭代、把取模换成条件减法（第 1 章 P1045 那个优化）
6真的是复杂度不够到最后才怀疑这一步。这时候要重新做第 1 章那件事：估一遍复杂度，看和 n 的范围对不对得上
4.6　五个真正管用的调试手法按性价比排序
  1. 小数据手推。先自己造一组 n = 3 的数据，用笔算一遍正确答案，再让程序跑一遍。这一步能定位一半的问题，而且不需要写任何工具。
  2. 打印中间量。把关键变量在关键位置打到 stderr，看它在哪一步开始偏离预期。不要用小黄鸭，用 fprintf。
  3. 二分定位。把程序从中间截断，看前半段的结果对不对 —— 一次砍掉一半的代码嫌疑。
  4. assert。把「我认为一定成立的事」写成断言，让它自己报出来。提交前记得关掉（或开 O2，一般会自动关）。
  5. 对拍。前三招都用完了还是找不到，就上第 3 章那套。它不猜，它直接给你一份出错的数据。

为什么建议打到 stderr 而不是 stdout？因为调试输出混进 stdout 会让你自己都分不清哪一行是答案、哪一行是调试信息，严重时还会直接把正确的答案挤成 WA。stderr 不参与答案比较，安全得多。

4.7　三个最贵的坑 + memset 的真面目原文里的「最贵三坑」，展开讲

坑一：爆 int

两个 10⁹ 相乘 = 10¹⁸，早就超过 int 的上限（约 2.1×10⁹）了。关键是 int × int 不会自动变成 long long —— 它是先按 int 算完（已经溢出、结果未定义），再赋值给 long long。

✗ long long s = a * b; // a、b 是 int → 先在 int 里爆掉 ✓ long long s = 1LL * a * b; // 先转 64 位，运算全程在 long long 里

看到乘法、求和、阶乘、组合数，先把默认类型设成 long long。别等到 WA 了再回来查。

坑二：数组开小了 1

下标从 1 开始，却只开了 n 个 —— a[n] 就是越界。规则：从 1 开始 → 开 n + 5。多开 5 个不占多少内存，但能省你一次 RE。

坑三：多组数据忘清空

第二组数据读到上一组的残留，答案莫名其妙。养成习惯：每个「多组数据」的题，读完第一行就先写清空。另外注意：全局数组只在程序启动时清零一次，不是每组数据都清。

memset 的真面目：它按字节，不按元素

memset(ptr, 值, 字节数) → 把每个【字节】都设成这个值

这是理解 0x3f3f3f3f 的唯一钥匙（第 2 章 2.3 讲过）：

  • memset(dist, 0x3f, sizeof dist) → 每个字节 = 0x3f，一个 int 有 4 个字节，拼起来是 0x3f3f3f3f = 1061109567（不是 63）
  • 它只能用来设 0、-1、0x3f 这类「每个字节都相同」的值。想全设成 1 是做不到的 —— 那样得到 0x01010101 = 16843009
  • 要按元素赋值就用 fill：fill(dp, dp + n + 1, -1e18)，想设什么设什么

5 · 离散化：把「很大的数」压成「很小的下标」

前四件是「做事的习惯」，这第五件是一件具体的前置技能。它本身只有十几行代码，但没有它，树状数组、线段树、扫描线这些结构有一大半题目都用不了。

5.1　本质与三步值域 10⁹ → 下标 n

本质：当数值很大（比如到 10⁹）但个数很少（比如 10⁵）时，我们往往只关心它们的相对大小，而不关心具体是多少。把「排序去重后的排名」当作新下标，值域就从 10⁹ 缩到 n。

三步：① 拷一份存起来 ② sort + unique 去重 ③ lower_bound 查排名（排名就是新下标）

原始值 [100, 3, 3, 55, 100, 3] → 排名 [3, 1, 1, 2, 3, 1]，映射表 {3→1, 55→2, 100→3}。值之间的「大小关系」被完整保留，这就是它能用的原因。

为什么需要它？因为「桶」和「树」这两种结构都要求下标是紧凑的整数。10⁹ 个桶开不出来（4 GB）；但 10⁵ 个桶、10⁵ 个节点的树状数组毫无压力。离散化做的事，就是把「值」翻译成「位置」。

5.2　完整模板（含 unique 的机制）最容易误解的一步

unique 不删除元素、也不改变容器长度，只是把不重复的挪到前面，然后返回「新逻辑结尾」的位置。

为什么 unique 必须配 erase

unique 的返回值是「新逻辑结尾」的迭代器，容器本身的 size() 一点没变。只调 unique 不 erase，后面那几个「已失效但还占着位置」的元素还会被 lower_bound 搜到 —— 排名就全错了。

b.erase(unique(b.begin(), b.end()), b.end()); └─ 返回新结尾 ─┘ └─ 从新结尾删到真正的末尾 ─┘

还要记住 unique 的前提：区间必须已经有序。它只去掉相邻的重复项。[3, 55, 3] 不排序直接 unique，结果还是 [3, 55, 3] —— 一个都没去掉。顺序永远是：先 sort，再 unique。

5.3　用到的四个函数：参数、返回值、复杂度一次讲清，不用再查
函数作用返回 / 复杂度最容易错的地方
sort(f, l) 把 [f, l) 升序排序，在 <algorithm> 无返回值 · O(n log n)，不稳定 左闭右开：对数组要写 sort(a, a + n)，不是 a + n − 1
unique(f, l) 把相邻的重复元素挪到后面，在 <algorithm> 返回新逻辑结尾的迭代器 · O(n) 不删除元素、不改长度；要求区间已有序；必须配 erase
lower_bound(f, l, x) 在有序区间里找第一个 ≥ x 的位置，二分实现 返回迭代器（全都 < x 时返回 l）· O(log n) 区间必须有序，否则结果随机；改成下发问 - begin() 拿 0-based 下标
v.erase(f, l) 删除一段区间，后面的元素整体前移 返回被删区间之后的第一个位置 · O(n) 删除会让后面的迭代器全部失效，别在遍历里随手 erase

顺带把 upper_bound 一起记了：它返回第一个 > x 的位置。
lower_bound(b, x) - begin() + 1 = x 的排名（从 1 开始，也是「比 x 小的个数 + 1」）
upper_bound(b, x) - lower_bound(b, x) = x 重复出现的次数
lower_bound(b, x) - begin() = 比 x 小的元素个数

5.4　离散化会丢掉什么什么时候不能这么干

这是原文里那句「要注意」的完整版 —— 也是唯一一个会让你用错离散化的地方。

判断标准就一句话：你要的是「顺序」还是「距离」？

问题在问什么能离散化吗例子
谁大谁小 / 排第几能第 k 小、比 x 小的有几个、排名、逆序对（只要比出大小）、去重后的种类数
相差多少 / 加起来是多少不能直接用区间和、加权和、两点距离、面积、计数（个数也要小心）

补救办法（很常用）：离散化时同时保留原值，用原值参与数值计算，用排名参与下标寻址，两者配对使用。

另一条路：不压缩坐标轴，改成只保留「关键点」。比如扫描线求矩形面积并，只用到矩形的 2n 条竖直边，把它们的 x 坐标离散化，这样区间长度可以靠相邻两个坐标的差算回来，距离信息并没有丢。

5.5　离散化之后能干什么它为什么是「前置技能」

值域从 10⁹ 降到 10⁵ 之后，一大批「下标必须紧凑」的结构才能用上：

解锁的东西离散化在这里做什么
树状数组求逆序对把数值当索引。原值 10⁹ 开不了那么大的数组，离散化后 n 个格子正好
线段树 / 主席树「第 k 小」「区间内第 k 大」—— 树的下标就是离散化排名
权值线段树同上，用排名当权值下标，才能统计「某个区间的数有几个」
扫描线求矩形面积并把 2n 条竖边的 x 坐标离散化，区间长度用相邻坐标差算
桶计数本来开 10⁹ 个桶是 4 GB；离散化后 n 个桶就能数了

一道题里它往往只是一行工具。所以真正要记住的不是「离散化怎么写」（第 5.2 节那 5 行已经够了），而是「什么时候该想到它」 —— 当你发现「值域很大、但个数不多」，而且想用「按下标寻址」的结构时，就该想起它。

5.6　离散化部分的六条常见错误第一条最常见

1. 用了 unique 却没有 erase

最常见的一条。容器长度没变，后面那些失效元素还会被搜到，排名整体错位。写成一行 b.erase(unique(b.begin(), b.end()), b.end()); 就不会忘。

2. 先 unique 才 sort

unique 只处理相邻重复。顺序必须是 sort → unique。写反了一个都去不掉，而且不报错。

3. lower_bound 之前忘了保证有序

lower_bound 是二分，区间无序时结果是随机的（不是报错，是安静地给你错答案）。所有 lower_bound / upper_bound / 二分查找都要求有序。

4. 忘记 +1 或 -1，1-based 与 0-based 混用

- b.begin() 得到 0-based；+1 变成 1-based。选一种用到底。混用的典型症状是「答案差 1」或者「最后一个元素丢失」—— 树状数组通常要 1-based（因为 lowbit(0) = 0 会死循环）。

5. 覆盖了原数组

直接 sort(a) 再离散化，原顺序就没了 —— 而很多题需要「原来的第 i 个数」。

6. 把「距离信息」也一起离散掉了

见 5.4。需要求和、算距离、算面积的题，离散化只能压缩坐标轴，不能压缩权值。离散化之后直接对排名求和，答案一定是错的。

自检清单（写完离散化立刻核对）：
① sort 和 unique 的顺序对吗？ ② 有 erase 吗？
③ 排名是 0 还是 1 开始，全文一致吗？ ④ 原数组有没有被破坏？
⑤ 这道题要的是「顺序」还是「距离」？
