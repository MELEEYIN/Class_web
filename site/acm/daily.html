1 · 复杂度分析：一分钟算出「能不能过」

复杂度分析不是数学，是一种手感。它要解决的唯一问题是：给我 n 的范围，我能不能在 1 秒内跑完？这个反应要快过想解法本身。

同样出现 n，一个是步数，一个是被减半的规模。判断依据永远是问自己一句：循环体每执行一次，那个决定循环次数的量发生了什么变化？

  • 每次 +1（或 += 常数）→ 线性，O(n) 次
  • 每次 ×2 / ÷2（n /= 2、b >>= 1）→ 对数，O(log n) 次
  • 每次 += i（步长本身就是变化的量）→ 调和级数，O(n log n) 次 ← 最容易翻车的一类
1.2　先判断「能不能过」增长曲线与 1 秒运算上限
O(log n) O(n) O(n log n) O(n²) O(n³) 1 秒上限

纵轴与横轴都是对数轴（分别为 10⁰–10¹² 次运算、10⁰–10⁶ 的 n）。曲线穿出顶边表示运算次数已超过 10¹²，不再有意义。

看这张图有两个要点：

  1. 纵轴是对数轴，视觉上的"陡"被压扁了。真实情况比图上可怕得多：n 从 10³ 涨到 10⁶（才 1000 倍），O(n²) 的运算量涨了 10⁶ 倍。
  2. 交点才是重点。O(n²) 大约在 n ≈ 10⁴ 处触线，O(n³) 在 n ≈ 460 处就爆了。这两个数要背下来 —— 拿到题先看 n 的范围，立刻能反推"这题允许我用什么复杂度的算法"。

工程上够用的换算：C++ 一秒大约 10⁸ 次简单运算（加减、比较、移位）。取模与除法慢 10～20 倍；递归调用和 STL 容器再打个折。所以实做时一般在 10⁷ ~ 10⁸ 这个区间卡安全线。

注意：复杂度是渐进行为，不是性能承诺。同一个 O(n log n)，手写归并和 std::sort 的常数差好几倍；同一个 O(n)，用 cin 读入和使用 scanf 也可能差一倍。

1.3　数据规模 → 可承受复杂度这张表建议直接背下来

按每秒约 10⁸ 次运算估算。颜色只表示"这一档算法的余量"，越靠上越贵。

做题时它是反向使用的：题目给出 n ≤ 5000，你就知道必须往 O(n²) 以内想，任何 O(n³) 的朴素思路都得当场毙掉 —— 不需要写出来再跑一次。

空间也要算。int a[100000000] 是 400 MB，直接 MLE。换成 bool 或 bitset 只有 12.5 MB。bitset<10⁸> 是 10⁸ 位而不是字节 —— 这个换算要能一眼看出来。

1.4　六种循环形状速查扫一眼形状就出结论

复杂度分析在实战里不是逐行推的，是扫一眼循环的"形"就出结论。这六种覆盖了 90% 的场景。

  • O(n)：i 每次 +1 走到 n，就是 n 次。前缀和、双指针都是这个形状。
  • O(n²)：两个独立变量各走 n 次，乘起来。Floyd 的三重循环里 k 在外层，本质还是 n×n 的两维状态表；冒泡排序比较次数是 n(n−1)/2 → 去掉系数还是 n²。
  • O(log n)：n 每次折半，问"能折多少次"。2^k ≤ n ⟹ k ≤ log₂n。它不跟 n 成正比，而跟 n 的位长成正比 —— n = 10⁶ 时 log₂n 只有 20。
  • O(n log n)，排序型：std::sort 是 O(n log n)，不是 O(n)。这是最常被白送的一条。
  • O(n log n)，嵌套型：外层线性、内层折半，两者相乘。KMP 里那个 while 的跳转是均摊 O(1) 的；树状数组每个操作 O(log n)。
  • O(n³)：三层嵌套。区间 DP、矩阵乘法、高斯消元。n = 500 就是它的天花板。

最容易吃亏的是第 4 种。有人在一个 O(n²) 的循环里顺手 sort 一遍，复杂度没变但常数翻了好几倍；更糟的是在 O(n log n) 的外层循环里 sort，直接退化成 O(n² log n)。

1.5　调和级数：最容易数错的形状步长是 i 而不是 1

这是这一节真正的技术核心。原文那个例子，放大来看：

看第二层，不要看 n，要看 j 怎么变。j 取的值是 i, 2i, 3i, … 直到超过 n，所以它的执行次数是 ⌊n / i⌋。于是总次数是各层相加：

总次数 = Σ(i=1..n) ⌊n / i⌋ = n · (1 + 1/2 + 1/3 + … + 1/n) = n · H(n)

H(n) 是调和数，H(n) = ln n + γ + O(1/n)，其中 γ ≈ 0.5772 是欧拉常数。所以：

n · H(n) ≈ n · ln n ≈ 0.693 · n · log₂ n ⟹ O(n log n)

以 n = 16 为例：每根柱子的高度就是内层的执行次数 n/i，柱顶落在双曲线 n/i 上。左边第一根一根就抵得上右边一堆 —— 面积按 n·ln n 增长，不是 n²。

为什么换底不影响复杂度：log_a n = log_b n / log_b a，只差一个常数因子，而 O() 里所有常数都丢掉。所以写复杂度时不必纠结 log 的底。

1.6　三层循环：系数丢掉，量级不变内层平均只走一半，仍然是 O(n³)

一层层数。内层 k 从 j 走到 n，次数是 n − j + 1。对 j 求和：

Σ(j=1..n) (n − j + 1) = n + (n−1) + … + 1 = n(n+1)/2

再乘上外层 i 的 n 次：

n · n(n+1)/2 = n²(n+1)/2 ⟹ O(n³)

系数是 1/2，但复杂度不写系数。这是这里唯一的考点：1/2·n³、100n³、n³ + 5n² 全都写成 O(n³) —— 因为大 O 只关心增长的量级，不关心常数。

由此得一条省事的判断法则：三层 for、每层变量都是 ±1 变化、边界都跟 n 同阶 → 答案基本就是 O(n³)。只有当某个循环变量的变化方式不是 ±1（j += i、k /= 2，或起点依赖外层且步长随外层变），量级才可能变成 n³ 以外的东西。

1.7　例题：洛谷 P1045 麦森数同一道题，两个子问题差 10⁶ 倍

这题的价值不在算法，在于它把"同一道题里，两个子问题的复杂度可以差好几个数量级"演示得极清楚。

题目：求 2ᵖ − 1 的位数与最后 500 位，p ≤ 3.1 × 10⁶（输出末 500 位，每行 50 位，共 10 行）。

第一问：位数 —— O(1)，一行公式

记 d(x) 为 x 的十进制位数，则 d(x) = ⌊log₁₀ x⌋ + 1。代入 x = 2ᵖ：

d(2ᵖ) = ⌊log₁₀ 2ᵖ⌋ + 1 = ⌊p · log₁₀ 2⌋ + 1

为什么 2ᵖ − 1 的位数和 2ᵖ 一样？因为 2 的幂的末位只可能是 2、4、8、6，永远不是 0，所以 2ᵖ 不是 10 的倍数，减一绝不会跨越 10ᵏ 这条边界。

p = 3.1×10⁶ 时：3.1×10⁶ × 0.3010299957 ≈ 933192.99 → 933193 位。

浮点精度够不够？够。double 有约 15.95 位十进制有效数字，而这里 p·log₁₀2 只有 6 位整数部分，绝对误差在 10⁻¹⁰ 量级，远小于 1，判定 ⌊·⌋ 绝对可靠。这题不需要高精度求位数 —— 很多人上来就写高精度，属于没估复杂度。

第二问：末 500 位 —— 必须高精度

思路是把"两位十进制"折成"八位十进制"来压块，同时利用"只乘 2"这个特殊结构把除法全部消掉 —— 因为底数固定是 2，进位只可能是 0 或 1，所以可以把最慢的 % 和 / 换成一次比较和一次减法。

复杂度：内层迭代 p × LEN ≈ 3.1×10⁶ × 65 ≈ 2×10⁸ 次。乘法和比较都很便宜，落在 1 秒的安全线内。

进阶写法：用快速幂把指数压到 log p。关键在于一个洞察 —— "只保留低 500 位"在乘法下是封闭的：进位只向高位走，高位不会反过来影响低位，所以每次乘完直接截断是合法的。这样只需要约 2·log₂p ≈ 44 次 500 位 × 500 位的乘法，每次约 65² = 4225 次块乘，总量约 2×10⁵ —— 比上面快三个数量级。

1.8　七条常见错误比上面所有内容都值钱

1. 把 O(log n) 写成 O(√n)

判别标准只有一个：看变量的变化方式。

试除法求单个数的质因数分解是 O(√x)，不是 log。记忆口诀：折半才是 log，逐个试永远是线性 —— 哪怕上界只有 √n。

2. 忘记 sort 也占时间

3. 忘记 STL 的隐性代价

  • map / set：每次操作 O(log n)
  • unordered_map：平均 O(1)，但最坏 O(n) —— 会被出题人专门构造数据卡掉
  • string 用 + 反复拼接是 O(长度)，在循环里拼就是 O(n²)
  • vector::push_back：均摊 O(1)（容量翻倍）

4. 输入输出本身也是复杂度

cin >> x 默认与 C 的 stdio 同步，慢 3～5 倍。10⁶ 级别读入时这是生死线：

5. 递归要看递归树，不是看代码行数

朴素斐波那契 f(n) = f(n−1) + f(n−2) 是 O(2ⁿ)；加一个记忆化数组后是 O(n)。同一个式子，两种复杂度，差别就是"有没有把重复子问题存下来"。

6. 只算时间不算空间

见 1.3 数据规模对照表 里的提醒：int[10⁸] 是 400 MB，bitset<10⁸> 只要 12.5 MB。

7. n 很小时，常数因子会反过来咬你

n = 100 时，一个循环体极简的 O(n²) 可能跑得比常数很大的 O(n log n) 快。复杂度是渐进行为，不是性能承诺 —— 这也是为什么"能不能过"要按实际 10⁸ 的基准去算，而不是只看阶。

2 · 竞赛代码脚手架：快读、快写与常用宏

把「每次都写一遍」的东西固化成模板，比赛时在编辑器里 Tab 一下出来。省下的不是几秒钟，而是打断思路的次数。但脚手架也是最容易埋坑的地方 —— 一层一层看，每层都要知道自己在拿什么换什么。

2.1　脚手架的四个层次每层的取舍不一样

脚手架不是「一堆宏」，而是四层职责完全不同的东西。分清楚层次，才知道哪些能省、哪些不能省。

越靠上的层，影响面越大：头文件决定「能不能编译」，宏只决定「代码短不短」。

一个反直觉的结论：四层里最不值得省的是第一层（头文件）。多写几个 #include 只花你两秒钟，写错一个头文件或者用了非标准的万能头，代价是换环境就编译不过。而最值得花时间打磨的是第三层（输入输出）—— 它直接决定会不会 TLE，而且改起来只有几行。

第四层（宏）要刻意克制：宏没有类型检查、没有作用域、报错信息指向宏定义而不是你的调用点。它能把代码写短，也能让你花半小时找一个本来 30 秒就能看出来的错误。

2.2　第一层：头文件 —— 为什么不该用万能头含 23 行对照表 + 一个中肯的例外

很多模板第一行是 #include <bits/stdc++.h>，看起来「一行顶所有」。它确实能在 GCC 上跑通 —— 问题在于代价。

问题说明
不是 C++ 标准的一部分它是 GCC 私有的实现细节（依赖 libstdc++）。换到 MSVC、部分 clang 的严格模式、某些评测机或真实工程里，直接编译不过。
编译明显变慢它把上百个标准头一次性展开。编译一个空程序：用万能头要 1 秒以上，只引 <cstdio> 不到 0.1 秒。小型 OI 题你感觉不到，但它会纵容你永远不看自己用了什么。
学不到「谁在哪个头文件里」面试、笔试、看别人代码、改真实工程时，这个知识是硬需求。早期养成按需 include 的习惯，成本最低。

一个中肯的例外（原文没说，但你应该知道）：在洛谷、Codeforces 这类 GCC 评测机上，万能头确实能用，而且省下的两秒钟在 3 小时比赛里也不是完全无所谓。所以这不是「道德问题」，而是一个成本判断：

  • 长期收益明确：按需 include 让你知道自己用了什么，这个能力会一直复利。
  • 短期代价极低：多写 3 行 #include。
  • 所以结论是「当习惯用按需」，而不是「用了万能头就是错的」。赶时间的正式比赛里用了也不必自责 —— 只要你知道代价是什么。
  • 但有两种场合绝对不要用：投简历的代码、任何给别人看/交付的工程代码。

<cstdint>int32_t / int64_t / uint64_t需要确定位宽时

隐藏得很深的一个坑：priority_queue（优先队列）在 <queue> 里，不在 <algorithm> 也不在 <vector>。还有 pair 在 <utility>（虽然 <map> 通常会顺手带上它）。这两个是「CE 找不到类型」的高频原因。

2.3　第二层：别名与常量 —— INF 为什么偏偏是 0x3f3f3f3f原文提到但没解释，这里补上
INT_MAX = 2147483647 = 0x7FFFFFFF 0x3f3f3f3f = 1061109567 （≈ 1.06 × 10⁹）

两个都是「很大的数」，为什么求最短路、做 DP 时几乎所有人用后者？三个原因，每一个都实在：

① 加自己不会溢出

松弛操作里最常见的一句是 dist[v] = min(dist[v], dist[u] + w)。如果 dist 的初值是 INT_MAX，那么当 dist[u] 还是无穷大时，dist[u] + w 就溢出了 —— 有符号整数溢出是未定义行为，结果是负数，于是「无穷大 + 边权」变成了一个很小的数，被当成更优解取走，答案彻底错掉。

INT_MAX + INT_MAX = 4294967294 > 2147483647 ✗ 溢出 0x3f3f3f3f × 2 = 2122219134 < 2147483647 ✓ 安全

用 0x3f3f3f3f 时，两个「无穷大」相加仍然小于 INT_MAX，所以松弛时不会翻车。

② 可以用 memset 一键初始化

memset 是按字节填充的，只能填「四个字节都相同」的值。

memset(a, 0x3f, sizeof a) → 每个字节 0x3f → int = 0x3f3f3f3f ✓ memset(a, 0x7f, sizeof a) → 得到 0x7f7f7f7f，并不是 INT_MAX ✗

所以 INT_MAX 根本没法用 memset 批量赋值，只能老老实实写 for 循环 —— 在 n = 10⁶ 的图上这就是一次白送的常数开销。

③ 余量刚好够用，不多不少

0x3f3f3f3f ≈ 1.06×10⁹ 比大多数题目的最短路上界（10⁹ 量级）大一点点，又比 INT_MAX 小一半，给「累加两三次」留出了空间。long long 版本对应的是 0x3f3f3f3f3f3f3f3fLL。

顺手一个同类坑：取模常量写成 const int MOD = 1e9 + 7; 是错的说法 —— 1e9 是 double 字面量，赋给 int 会发生隐式转换。直接写 1000000007，或者写成 const ll MOD = 1e9 + 7;。需要整型常量的场合（constexpr、模板参数、位运算）会因此出意外。

2.4　第三层：快读 —— 什么时候才真的需要10⁵ 以下不用写，纯属自我感动

先看结论再决定要不要写：只有在输入量 ≥ 10⁶ 时，手写快读才有实际收益。读 10⁵ 个数，所有方式的差距都在 0.1 秒以内，而你手写快读多花的调试时间远不止这些。

五种输入方式的量级对比

如果不想手写快读，只加一行就够了：

两条硬性约束（踩了就是玄学 WA / 顺序错乱）：

  • 必须在任何 IO 之前调用，习惯上就写在 main 第一行。写在中途等于没写。
  • 调用之后不能再混用 printf / scanf：两者各用各的缓冲区，输出顺序会乱套。
  • 交互题不要写 cin.tie(nullptr)：关掉绑定后你的输出可能不立刻发出去，对方一直在等，直接 TLE。

手写快读：getchar 版（通用）

为什么 if (c == EOF) return 0; 是必须的？因为 EOF 的值是 −1，而 −1 < '0' 恒成立 —— 读到文件末尾后 getchar() 会一直返回 EOF，第一个 while 的判断条件永远为真，程序就卡在那里了。这是手写快读最经典的死循环。

手写快读：fread 版（更快，输入量到 10⁷ 再考虑）

思路是「一次读一大块进内存，之后从内存里取字符」，把上千次系统调用压缩成几十次。

什么时候不必手写快读：输入量在 10⁶ 以下、或者你正在第一遍写思路。先把 cin 优化那两行加上，跑 TLE 了再换快读 —— 这是性价比最高的顺序，因为快读本身也是容易写错的代码。

2.5　第三层：快写 —— 以及 endl 这个 TLE 元凶换行符的代价比你想象的大
endl = 换行 "\n" + 强制刷新缓冲区 flush()

很多人把 endl 当换行用。它每次都会 flush —— 输出 10⁶ 行时就是 10⁶ 次系统调用，慢好几倍，是 TLE 的常见原因之一。只要换行就写 "\n"。

缓冲版快写（输出量 ≥ 10⁶ 时用这个）

最容易忘、也最难查的一步：缓冲版快写如果不手动 fwrite 收尾，最后不到 1 MB 的输出会全部丢掉。表现是「本地对、交上去 WA，而且只错最后几行」—— 因为本地调试时数据小，缓冲没满过，反而不触发。养成习惯：在 return 0; 前固定加一行 flush。

2.6　第四层：常用宏 —— 该用的、要小心的、不要用的这一节最能拉开差距

宏在 C++ 里是「文本替换」，它没有类型检查、没有作用域、报错时指向宏定义而不是你的调用点。所以判断标准很简单：这个宏会不会在你没防备的时候悄悄改变语义？

分档依据只有一条：调用点有没有可能出现「你没想到的展开结果」。

为什么 #define int long long 是毒宏

它看起来能「一键防溢出」，一次解决所有爆 int 的烦恼。代价是三个：

  1. 所有 int 型数组内存直接翻倍。int a[10⁷] 从 40 MB 变成 80 MB，原本能过的题变成 MLE。
  2. printf("%d", x) 输出错乱。x 实际是 64 位，而 %d 按 32 位解释 —— 这是未定义行为，结果莫名其妙（要改成 %lld，可你满屏都是 %d）。
  3. int main() 会变成 long long main()，编译不过。于是你被迫写 signed main() —— 用另一个非标准的写法去补前一个的洞。一个坑引出两个坑，这就是它最坏的地方。

同样危险的「函数式宏」

三条能省下大量调试时间的规则：

  1. 宏只用来写「控制流简写」（rep / per / all），不用来写「求值」。凡是参数会被计算的东西，一律用 inline 函数或模板。
  2. 所有宏名加长度：mx → mxv、mn → mnv、l → lft、r → rgt。宏是全局文本替换，撞车时报错信息完全指不到问题所在。
  3. 宏体里每个参数都加括号、整体再加一层括号，否则 sqr(a + b) 会变成 a + b * a + b。

2.8　脚手架部分的九条常见错误每一条都真的会让人卡住

1. 快读里没判 EOF → 死循环

EOF = −1，而 −1 < '0' 恒真，所以跳过非数字的第一个 while 永远成立。必须在里面加 if (c == EOF) return 0;。

2. 用 char 接 getchar() 的返回值

getchar() 返回 int，因为要在 0~255 之外再表示一个 EOF。用 char 接的话，EOF 和字符 0xFF 混在一起，EOF 判断直接失效，接着就是死循环或乱码。

3. 混用 printf 和 cin

写了 sync_with_stdio(false) 之后两者各用各的缓冲，输出顺序会乱。选一套用到底。

4. sync_with_stdio(false) 写在读入之后

它必须在任何 IO 发生之前调用。写在 main 中间或某个函数里等于没写。

5. 用 endl 当换行

每次强制 flush。输出 10⁶ 行能慢好几倍，是 TLE 高频原因。

6. 缓冲快写忘了收尾 flush

最后不到 1 MB 的输出全部丢失，表现是「本地对、交上去只错最后几行」。

7. const int MOD = 1e9 + 7;

1e9 是 double 字面量。写 1000000007。

8. 大数组开在 main 里（局部变量）

局部变量在栈上，Windows 默认栈只有 1~8 MB。int a[1000005] 是 4 MB，看起来没事，但多开几个就 RE（而且是「莫名奇妙的 RE」，因为栈溢出不会给你友好的提示）。一律写成全局变量，或加 static。

9. 忘记 assert 要关掉

assert 在本地帮你自检很爽，但正式提交时如果没定义 NDEBUG，它会被执行 —— 大循环里的 assert 可能直接把程序拖成 TLE。开 O2 通常会自动关掉，但别赌。

还有一个跨平台的坑（对拍时最常撞）：RAND_MAX 在 Windows 上只有 32767，Linux 上是 2³¹−1。所以 rand() 在 Windows 本地根本出不了大数 —— 想生成 10⁶ 级的随机数得手动拼：rand() * rand() 或 (rand() << 15) ^ rand()，或者直接用 <random> 的 mt19937。
